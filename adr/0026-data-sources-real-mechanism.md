# 0026 — Data & Sources: real mechanism (persistence, provenance/timestamp/reliability wiring, SourceFetcher seam)

**Status:** Accepted — 2026-08-26
**Component:** Data & Sources (02)

## Context

Data & Sources was whiteboard-only before this pass: `src/components/c02_data_sources.py` held a `DataSources` Protocol, its dataclasses (`Source`, `SourceType`, `SourceDocument`, `SourceSnapshot`, `Provenance`, `SourceMetadata`), and a `StubDataSources` traced no-op — no mechanism design, no ADRs. This project's operating mode for this pass is to build end to end using engineering judgment rather than pausing for design-tradeoff questions, and to document each real call as an Accepted ADR with the same rigor as every prior one, not a Proposed draft — that is what this ADR is.

Three genuine forks came up while making `DefaultDataSources` real, all real enough to warrant naming here rather than deciding silently:

1. **Persistence shape.** `DefaultInfrastructure` (ADR-0019) exposes `store`/`retrieve`/`query` against a named table; this component's assignment named `"sources"` specifically. But this component's own Protocol needs to persist several different entity shapes off the same `source_id` — a `Source` registration, its most recently ingested `SourceDocument`, its provenance tag, its tracked timestamp, its reliability metadata — and `Infrastructure.store` keys rows by `(table_name, id)`.
2. **Provenance/timestamp/reliability wiring.** `track_source_provenance`, `track_source_timestamp`, and `track_source_reliability_metadata` are listed as standalone Protocol methods, but ADR-0003 requires every document to be tagged UNTRUSTED before it's reasoned over elsewhere — the question is whether that tagging is something a caller has to remember to invoke separately, or something this component does automatically at the point a `SourceDocument` is produced.
3. **The external-fetch seam.** `ingest_source` is the one capability that cannot be made fully real without a live external credential (news/filing/market-data API) this project doesn't have. That specific provider choice is out of scope for this ADR — it's the genuine external-credential exception, handled in ADR-0027 (Proposed) — but the *shape* of the seam `ingest_source` calls through to reach that eventual provider is a real design decision made now, independent of which provider gets picked later.

## Decision

**1. Single `"sources"` table, namespaced row ids, one entity shape per `record_kind`.** Rather than one table per entity kind (`source_documents`, `source_provenance`, ...), every record this component writes goes into the one `"sources"` table its assignment named, distinguished by a `"record_kind"` field (`"source"`, `"source_document"`, `"provenance"`, `"timestamp"`, `"reliability_metadata"`) and a composite row id (`f"{kind}::{source_id}"`, e.g. `document::AAPL-10K`) so the five shapes never collide on `(table_name, id)`. `discover_source`'s `criteria` filters against `{"record_kind": "source", **criteria}` so a query never accidentally matches a document or metadata row.

**2. Every produced `SourceDocument` is tagged and stored automatically, not on request.** `ingest_source` and `update_source` (which re-ingests) both call `track_source_provenance` and `track_source_timestamp` internally as part of producing a document, in addition to those methods remaining independently callable per the Protocol. `track_source_provenance` routes through `DefaultBoundaryGate.tag_provenance` (ADR-0003) for real and persists the resulting tag; nothing reaches storage untagged.

**3. `SourceFetcher`: one injectable interface across every `SourceType`, not one per type.** `ingest_source` calls through a single `SourceFetcher.fetch(source: Source) -> SourceDocument` seam, dispatched by `source.type` inside whatever concrete fetcher is injected, rather than exposing `NewsFetcher`/`FilingFetcher`/`MarketDataFetcher` as separate Protocols `DefaultDataSources` would need to route between itself. The only implementation shipped today, `PlaceholderSourceFetcher`, returns a `SourceDocument` whose content is the unmistakable `PLACEHOLDER_FETCH_MARKER` constant (never empty bytes, which could be confused with a legitimate empty response) for every source and every type alike, with a real timestamp of when the placeholder ran. `track_source_reliability_metadata` uses that same marker to score placeholder-backed documents lower (`_RELIABILITY_SYNTHETIC_DOCUMENT = 0.3`) than a genuinely fetched one would (`_RELIABILITY_REAL_DOCUMENT = 1.0`) — a real, honestly-computed signal that happens to always report the lower score today, because no real fetcher exists yet.

## Alternatives considered

- **One table per entity kind** (`sources`, `source_documents`, `source_provenance`, `source_timestamps`, `source_reliability`). Cleaner per-entity schemas and no `record_kind` discriminator needed, but the task explicitly named `"sources"` as the table to persist through, and five tables for what is fundamentally one component's bookkeeping around one `source_id` felt like over-partitioning relative to `Infrastructure`'s deliberately simple JSONB-containment `query()` (documented in `infrastructure_postgres.py` as "not a general query DSL, deliberately kept simple for this first version"). Not chosen.
- **Leave provenance/timestamp tagging caller-invoked only** (Protocol methods exist, but `ingest_source` doesn't call them). Matches the Protocol's literal method list most narrowly, but silently reproduces the exact risk ADR-0003 exists to close: an untagged `SourceDocument` could reach Data Processing & Quality (03) and be reasoned over as if it were trusted, if whatever caller consumes `ingest_source`'s return value forgets the separate tagging step. Not chosen — the task instruction was explicit that this wiring should be real, not just noted.
- **A `SourceFetcher` per `SourceType`** (`NewsFetcher`, `FilingFetcher`, `MarketDataFetcher`, ...). Would let each real implementation's interface shape differ by source type (e.g. a market-data fetcher might want a symbol + date range, not just a generic `Source`), which is a real advantage a unified interface gives up. Not chosen for this pass because nothing about `Source`/`SourceDocument`'s current shape (both are generic across every `SourceType`) demands type-specific fetch parameters yet, and a single interface keeps `DefaultDataSources.ingest_source` from needing to know which fetcher to call — that dispatch, if ever needed, can move inside a concrete `SourceFetcher` implementation without changing this Protocol. If a real provider integration later needs genuinely different parameters per type, that's a real reason to revisit this — noted here rather than pretended away.
- **Reliability metadata as a hardcoded constant** (e.g. always 0.0 until a real fetcher exists). Simpler, but throws away a real, computable signal: whether a document was ever successfully ingested at all is meaningful information downstream even before any real fetcher exists, and the synthetic/real distinction this ADR picks costs nothing extra to compute. Not chosen — see `track_source_reliability_metadata`'s docstring for the three-tier scoring this ADR does use instead.

## Consequences

- `register_source`, `discover_source`, `retrieve_source`, `update_source`, `track_source_provenance`, `track_source_timestamp`, and `track_source_reliability_metadata` are all real, `Infrastructure`-backed logic today — no in-memory dict, no hardcoded stub return.
- `ingest_source` is real orchestration (fetch → tag → timestamp → persist) around a fetch step that is not yet real content — see ADR-0027 for exactly what's missing and why. Anything downstream that depends on `ingest_source` returning genuinely fetched content is not yet safe to build on top of `PlaceholderSourceFetcher`.
- Every `SourceDocument` this component stores carries a persisted UNTRUSTED provenance tag before it can be retrieved again — `retrieve_source` itself doesn't re-check the tag (it wasn't asked to), but the tag exists in storage for whatever calls `track_source_provenance` again or reads the `"provenance"` record directly.
- `discover_source`'s `criteria` argument must match the stored representation exactly (e.g. `{"type": "NEWS"}`, matching `SourceType.NEWS.name`, not the enum member itself) — inherited directly from `Infrastructure.query`'s JSONB-containment semantics, not a new constraint this component invents.
- Once ADR-0027 is resolved and a real `SourceFetcher` implementation exists, the fix is narrowly scoped: implement `SourceFetcher.fetch` for real and pass it into `DefaultDataSources(source_fetcher=...)` instead of relying on the `PlaceholderSourceFetcher` default. No method on `DefaultDataSources` needs to change shape for that swap, mirroring ADR-0021's same claim for Agent Runtime's `reason_fn`.
