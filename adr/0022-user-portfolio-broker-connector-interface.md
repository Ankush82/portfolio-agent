# 0022 — User & Portfolio broker connector: injectable Protocol, untrusted by default

**Status:** Accepted — 2026-08-26
**Component:** User & Portfolio (01)

## Context

User & Portfolio has been whiteboard-only until this pass: a `UserPortfolio(Protocol)` / `StubUserPortfolio` pair in `src/components/c01_user_portfolio.py`, no mechanism design, no ADRs. This pass implements `DefaultUserPortfolio`, the component's first real logic.

Three of its nine methods — `connect_portfolio`, `import_holdings`, `import_transactions` — genuinely cannot be implemented for real right now: they need a live broker or DMAT (depository account) connection, which means a live external credential (an API key, an OAuth grant, a real brokerage account) this project does not have. That's the standing exception this project already uses elsewhere (ADR-0020's `authorize()`, ADR-0021's `reason_fn`): inject a placeholder behind a real interface, so the rest of the component can be built and tested around the gap, and raise the actual provider choice as its own Proposed ADR rather than deciding it inside an implementation pass. That provider choice is ADR-0023.

What ADR-0023 does *not* cover, and what remains a real decision this pass has to make, not defer: what shape does the seam itself take (a `Protocol` with explicit methods, vs. a single injected `Callable`), and what happens to data that comes back through it before it reaches the rest of the component. Those are code-structure questions this project already has the information to answer today — they don't require knowing which broker gets chosen.

## Decision

**Interface shape: a `Protocol`, not a `Callable`.** `BrokerConnector` exposes three methods — `connect(user, broker_credentials) -> dict`, `fetch_holdings(portfolio) -> list[dict]`, `fetch_transactions(portfolio) -> list[dict]` — mirroring the three `UserPortfolio` methods that need it. A single `Callable[[dict], dict]` (the shape ADR-0021 chose for Agent Runtime's `reason_fn`) was considered and rejected here: Agent Runtime's `reason_fn` is one call site behind one interface responding to a `phase` field in its input, which fits a single dispatch function. `BrokerConnector` backs three methods with three different real-world operations (establishing a session vs. two different kinds of read), each with its own natural argument and return shape (`User`+credentials vs. `Portfolio` alone). Forcing that through one `Callable` would mean either three separate injected callables (no real benefit over three Protocol methods) or one dispatch dict with a phase discriminator, which adds indirection this component doesn't need — `UserPortfolio` itself is already a `Protocol`, and `BrokerConnector` following the same pattern keeps the codebase's two connector-style seams (this one, and Infrastructure's) shaped the same way.

**Placeholder implementation: `PlaceholderBrokerConnector`.** Ships as the only concrete `BrokerConnector` today. `connect()` returns a synthetic dict tagged with a generated placeholder account identifier and `"broker": "placeholder"` — enough structure for `DefaultUserPortfolio.connect_portfolio` to build a real `Portfolio` around it, but a value no real broker would ever return. `fetch_holdings()` and `fetch_transactions()` return empty lists rather than synthetic positions or trades: inventing fake holdings/transaction amounts would look like real financial data to anything downstream that doesn't already know this path is a placeholder (Decision & Policy, Analysis & Reasoning, a human reading a snapshot) — an empty list is unambiguous in a way synthetic numbers aren't. Its class docstring and every method's docstring say plainly that it is not a real broker connection.

**Provenance: broker-sourced data is tagged UNTRUSTED at the point it enters `DefaultUserPortfolio`, before it's used to build any `Holding`/`Transaction`/portfolio-connection record.** This extends the same pattern ADR-0003 established for document content entering Agent Runtime's loop and ADR-0018 extended to delegated sub-agent output: content originating outside this system's own trust boundary gets tagged before anything downstream can reason over it as though it were verified. A broker API response is exactly that kind of boundary crossing — arguably more so than peer-agent output, since it's the one path in this component that talks to a real external system once ADR-0023 is resolved. `DefaultUserPortfolio.connect_portfolio`/`import_holdings`/`import_transactions` all route the connector's raw return value through `BoundaryGate.tag_provenance` (`DefaultBoundaryGate` by default) before constructing the typed dataclass the `UserPortfolio` Protocol promises to return, and persist the tagged record (including its `provenance` field) via `Infrastructure.store` for audit purposes — the returned `Holding`/`Transaction`/`Portfolio` objects stay exactly the shape the Protocol already declares; the tag lives in what gets stored, not in a widened return type.

## Alternatives considered

- **`Callable[[dict], dict]`, matching ADR-0021's `reason_fn` shape exactly**, for consistency across the codebase's two "we don't have the real backend yet" seams. Rejected: consistency for its own sake isn't a reason when the two seams don't actually have the same shape — `reason_fn` genuinely is one operation with a phase discriminator; `BrokerConnector` genuinely is three different operations. Forcing sameness here would trade real clarity (three named methods, each independently testable and independently swappable when ADR-0023 resolves) for surface consistency with a different problem.
- **No provenance tagging on broker data**, treating it as trusted once ADR-0023 picks a real, presumably reputable, broker or aggregator API. Rejected: ADR-0003 and ADR-0018 already established that *this project's* standard is to tag by origin (inside vs. outside this system), not by presumed reputability of the source — a legitimate broker API is still external content the runtime hasn't independently verified, and carving out an exception here would be deciding, quietly, that broker data is somehow different from document content or peer-agent output without any stated reason it actually is.
- **Tag at read time (wherever `Holding`/`Transaction` records are later retrieved) instead of at write time (`import_holdings`/`import_transactions` themselves).** Rejected for the same reason ADR-0007 rejected trust-weighted-at-read for Memory: tagging late means anything that reads the untagged intermediate state before the tag would have been applied sees unlabeled external data. Tagging at the point of ingestion, before the dataclass is even constructed, is the only place that's guaranteed to run exactly once per broker response.

## Consequences

- `BrokerConnector` and `PlaceholderBrokerConnector` are real, tested code today; nothing about `connect_portfolio`/`import_holdings`/`import_transactions`'s control flow, persistence, or provenance tagging needs to change when ADR-0023 resolves — only `PlaceholderBrokerConnector` gets swapped for a real implementation of the same three-method `Protocol`, the same shape ADR-0021 already established for `reason_fn`'s eventual replacement.
- Until ADR-0023 resolves, `connect_portfolio` always produces a `Portfolio` with no real broker session behind it, and `import_holdings`/`import_transactions` always produce empty lists. `synchronize_portfolio` and `track_portfolio_state`, which read from what's been imported, are correspondingly empty for any portfolio that has never had holdings/transactions stored some other way (e.g., directly through `Infrastructure.store` in a test or a future data-migration path). This is the honest consequence of the underlying gap, not a bug in this component's logic.
- Every broker-sourced record now carries a `provenance` field in storage. Nothing downstream of `Infrastructure.retrieve`/`query` currently reads that field to change its own behavior (no component has an "act differently on UNTRUSTED input" rule yet beyond Agent Runtime's own runtime tagging) — the tag is present and auditable, not yet enforced against anywhere in this component.
