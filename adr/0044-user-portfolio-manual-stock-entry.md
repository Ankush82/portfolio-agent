# 0044 — User & Portfolio manual stock entry: a real, parallel onboarding path bypassing BrokerConnector

**Status:** Accepted — 2026-08-26
**Component:** User & Portfolio (01)

## Context

ADR-0022 gave `DefaultUserPortfolio` a real `BrokerConnector` seam for `connect_portfolio`/`import_holdings`/`import_transactions`, and ADR-0023 named the real broker/aggregator options (Zerodha Kite Connect, Upstox, the RBI Account Aggregator framework) without picking one, since that decision needs a live external credential this project does not have. That gap is being deferred indefinitely, not resolved by this pass — nothing about ADR-0022/ADR-0023 changes here.

Deferring the broker path indefinitely leaves this component with no working way to get real holdings into a `Portfolio` at all: `PlaceholderBrokerConnector` always returns empty lists (by design, ADR-0022), so every user onboarded through `connect_portfolio` alone has an empty portfolio forever. That's honest given the actual gap, but it means nothing downstream (`track_portfolio_state`, `calculate_exposure`, `determine_user_relevance`, and everything in Decision & Policy / Interaction & Notification that eventually consumes a `PortfolioSnapshot`) has real data to exercise until a broker is chosen. A second, genuinely independent onboarding path — a user manually selecting securities they already know they hold and entering a quantity — needs no external credential at all: it is a real, self-contained capability this project can build today, not another placeholder-behind-an-interface deferral.

The "dropdown" framing in the task that produced this ADR is a UI description; this project has no frontend/UI layer (`design-framework.md`'s scope is backend components only). What a dropdown needs is a real backend capability to call: a way to list selectable securities, and a way to add one to a portfolio by id. Both are implemented here as real methods, not a rendered UI.

The dropdown's list of options has to come from somewhere real. Knowledge & Entity Model (component 04, ADR-0035) is this project's actual registry of known entities — `DefaultKnowledgeEntity`, `Infrastructure`-backed, already used for real by Retrieval & Context (`DefaultRetriever.resolve_entity`, c05). Reusing it here, rather than hardcoding a static ticker list, keeps this feature honest about what the system actually knows: a fresh, unseeded system has an empty registry, and `list_available_securities` returning an empty list in that state is the correct answer, not a bug to mask with fabricated seed data (no ADR or design artifact anywhere in this project seeds the entities table with real securities — inventing that here, inside an onboarding-path ADR, would be deciding a data-sourcing question this pass has no basis to decide).

## Decision

**Two new methods on `DefaultUserPortfolio`, not on the `UserPortfolio` Protocol.** `list_available_securities(query: str = "") -> list[Entity]` and `add_holding_manually(portfolio: Portfolio, security_id: str, quantity: float) -> Holding`, plus `add_transaction_manually(portfolio: Portfolio, kind: str, amount: float) -> Transaction` (see below). None of the three go on `UserPortfolio(Protocol)`. This follows the exact precedent ADR-0029 already established for `DefaultEvidenceLinker.link_with_context()` in component 09: manual entry is an implementation detail of *how* User & Portfolio gets its data, not a new capability the rest of the system needs to know about. Everything downstream of this component — `synchronize_portfolio`, `track_portfolio_state`, `calculate_exposure`, `determine_user_relevance`, and every other component that eventually consumes a `Holding`/`Transaction`/`PortfolioSnapshot` — already only sees those dataclasses, indifferent to whether a `Holding` arrived via `import_holdings` or `add_holding_manually`. Widening the Protocol would force `StubUserPortfolio` and every future `UserPortfolio` implementation to carry a manual-entry method whether or not they have one, for no consumer that actually needs it through that interface.

**The dropdown's list of options is `DefaultKnowledgeEntity`'s real registry, filtered by kind, not a hardcoded list.** `list_available_securities` calls two new real methods added to `DefaultKnowledgeEntity` (component 04) for this: `search_entities(kind: str | None = None, query: str = "") -> list[Entity]`, which enumerates live (non-tombstoned) entities filtered by `kind` and, when `query` is non-blank, by a case/whitespace-normalized substring match against name/aliases (reusing `resolve_entity`'s own `_normalize_name`); and `get_entity(entity_id: str) -> Entity | None`, a direct id lookup that redirects a merged-away id to its surviving entity (the same redirect `update_knowledge` already applies), as opposed to `resolve_entity`'s mention/name-based fuzzy match. Neither is part of the `KnowledgeEntity` Protocol — same "extra real-behavior accessor" pattern `DefaultQuarantineGate.release()`/`is_expired()` (c06_memory.py) and `DefaultEvidenceLinker.link_with_context()` (c09) already establish: real behavior a fixed Protocol signature has no room for, added directly to the concrete class. `resolve_entity` genuinely can't serve either job here — it resolves one free-text mention to at most one entity; it has no enumeration mode, and using it to validate an id (by passing the id as if it were a name to fuzzy-match) would be an abuse of what it's built to do. `list_available_securities` filters to `Entity.kind` values that mean "a user could hold a position in this": `"Security"` and `"Company"` (`Entity.kind`'s own documented vocabulary is `Company | Security | Person | Sector | Industry | Index | Geography` — the other five are never something a `Holding.security_id` should point at), calling `search_entities` once per kind and deduplicating by id.

**`add_holding_manually` validates `security_id` via `get_entity` before constructing anything**, per this task's own instruction that a security_id that doesn't resolve must fail clearly rather than silently create a holding for a nonexistent security. It raises `ValueError` naming the bad id. `get_entity`, not `resolve_entity`, is the right validator here: `security_id` is expected to be an id a caller already obtained from `list_available_securities`'s own output (an `Entity.id`), not a free-text name a user typed — validating it should be a direct lookup, not a second, redundant fuzzy match over the string.

**`add_transaction_manually` is implemented too**, mirroring `import_transactions`'s existing `(kind, amount)` shape for consistency, per this task's "your call, implement it if it's a small, real addition." `Transaction` (c01's own dataclass) carries no `security_id` field, so there is nothing to validate against Knowledge & Entity Model here — it is a plain, direct write, smaller than `add_holding_manually`.

**Neither manual method tags its data `Provenance.UNTRUSTED`.** This is a deliberate contrast with ADR-0022's broker-data tagging, not an oversight. `DefaultBoundaryGate.tag_provenance` (ADR-0003/ADR-0018/ADR-0022) exists to mark content that crossed in from *outside this system's own trust boundary* — a document, peer-agent output, or a broker API's payload the system doesn't independently verify. A manually-entered holding is different in kind: it is a user directly selecting one entry from an already-known, already-validated internal registry (validated for real, via `get_entity`, before any `Holding` is built) — not an arbitrary external payload. This matches the precedent already set inside this same file: `onboard_user` and `manage_preferences` both write direct user-supplied data (`details`/`updates`) without ever calling `tag_provenance` either. Extending that same untagged treatment to manual holdings/transactions keeps the rule consistent — "direct, structured user input into this system's own onboarding flow" stays untagged; "content that arrived through an external system's API or a peer agent" gets tagged — rather than inventing a third, unprincipled category.

**`traced()` wraps every new method**, on both `DefaultUserPortfolio` and `DefaultKnowledgeEntity`, matching the project-wide convention every other method in both files already follows.

**`DefaultUserPortfolio.__init__` gains `knowledge_entity: DefaultKnowledgeEntity | None = None`**, defaulting to a `DefaultKnowledgeEntity` constructed against this same `DefaultUserPortfolio`'s own `Infrastructure` instance (so both components share one backing store rather than two independent connections). The parameter is typed against the concrete `DefaultKnowledgeEntity`, not the `KnowledgeEntity` Protocol, for the same reason `get_entity`/`search_entities` aren't on that Protocol: `DefaultUserPortfolio` genuinely needs those two extra methods, and typing the parameter against the narrower Protocol would misstate what this component actually calls.

## Alternatives considered

- **A hardcoded static list of tickers/companies for `list_available_securities`.** Rejected outright: this task explicitly calls for the real registry, and a static list would drift from whatever Knowledge & Entity Model actually knows, duplicate data ownership across two components, and — worse — mask a currently-true, honest fact about this system (nothing has seeded the entities registry yet) behind fake plausibility. An empty list from an empty registry is the correct signal; a hardcoded list would hide it.
- **Seeding the entities registry with real securities as part of this pass**, so `list_available_securities` would return something non-empty today. Rejected: seeding real security data is a Data & Sources (component 02) / Data Processing & Quality (03) concern — deciding *which* securities, from *what* source, with *what* provenance, is a real data-sourcing question this ADR has no basis to answer, and component 02 is still whiteboard-only per ADR-0026's own scope. Manufacturing seed data here to make a demo look populated would be exactly the "paper over an empty state with fake data" failure mode this task explicitly warned against.
- **Widening the `UserPortfolio` Protocol to add these three methods**, so every implementation (including `StubUserPortfolio` and any future one) carries them. Rejected for the same reason ADR-0029 rejected widening `EvidenceLinker`: these three methods are how this one concrete implementation happens to source its data, not a capability the rest of the system reasons about through the Protocol boundary. Nothing downstream calls `UserPortfolio.list_available_securities` polymorphically the way it calls `onboard_user` or `track_portfolio_state` — only a caller that specifically wants the manual-entry path calls it, and that caller already has to know it's talking to `DefaultUserPortfolio` (or something that duck-types the same extra methods) to get a `DefaultKnowledgeEntity`-backed answer in the first place.
- **Validating `security_id` via `resolve_entity(security_id)`** instead of adding `get_entity`. Rejected: `resolve_entity` treats its argument as a free-text mention and fuzzy-matches it against every entity's name/aliases — passing an opaque id through that path would either coincidentally string-match something unrelated (a false positive) or, far more likely, match nothing at all even for a perfectly valid id (a false negative), since ids and names are different strings by construction. A direct id lookup is what "does this id resolve to a real entity" actually means; `get_entity` is that lookup, done for real rather than approximated through the wrong mechanism.
- **Tagging manually-entered holdings `Provenance.UNTRUSTED`, for uniform treatment with broker data.** Rejected: `Provenance` in this codebase marks a real thing (data that crossed this system's own trust boundary from outside), not a generic "handle with care" flag applied to every write path. Applying it here would blur a distinction the project has been careful to keep sharp since ADR-0003, and would be inconsistent with `onboard_user`/`manage_preferences` already treating direct user input as untagged in this exact file.
- **A single `KnowledgeEntity.list_entities()` with no kind filter, leaving the "which kinds count as tradeable" decision to the caller inline.** Considered and rejected in favor of `search_entities(kind=...)`: `query_relationships(entity, kind: str | None = None)` already establishes the "optional kind filter, done at the component-04 level" shape in this same file, and doing the kind filtering inside `search_entities` means any future caller wanting "every live `Security`" gets a real, reusable primitive rather than reimplementing the same registry scan.

## Consequences

- A user can now get a real, non-empty `Portfolio` today, without ADR-0023 ever resolving — as long as Knowledge & Entity Model's registry has at least one `Security`/`Company` entity in it (created via `DefaultKnowledgeEntity.create_entity`, e.g. by a future Data & Sources/Data Processing & Quality pipeline, or directly in a test). On a genuinely fresh, unseeded system, `list_available_securities` honestly returns `[]` and `add_holding_manually` honestly rejects every `security_id` — this path does not manufacture data the registry doesn't have, it only removes the *broker* dependency, not the *registry-has-something-in-it* dependency.
- `add_holding_manually`/`add_transaction_manually` write to the same `HOLDINGS_TABLE`/`TRANSACTIONS_TABLE` rows `import_holdings`/`import_transactions` already write to (same row-id scheme, same dataclass shape), minus the `provenance` key. Every downstream reader (`_stored_holdings`, `track_portfolio_state`, `calculate_exposure`, `determine_user_relevance`) reads holdings/transactions structurally, never branching on the presence or absence of `provenance` — so a manually-added holding flows through every one of them identically to a broker-imported one. This is verified directly by a new test asserting a manually-added holding produces correct `calculate_exposure` output.
- `DefaultKnowledgeEntity` now has two public methods (`get_entity`, `search_entities`) beyond its own `KnowledgeEntity` Protocol, in addition to its existing full Protocol implementation — a small, real widening of that class's surface, justified the same way ADR-0029 already justified `DefaultEvidenceLinker`'s.
- `connect_portfolio`/`import_holdings`/`import_transactions` and everything ADR-0022/ADR-0023 decided about them are completely unchanged. This ADR adds a parallel path; it does not touch, simplify, or replace the broker path in any way.
