# 0023 — User & Portfolio broker/aggregator API choice: interim placeholder behind BrokerConnector

**Status:** Accepted — 2026-08-26
**Component:** User & Portfolio (01)

## Context

`DefaultUserPortfolio` (ADR-0022) now has real logic for onboarding, preferences, portfolio-state assembly, exposure calculation, and event relevance — everything that doesn't require talking to an outside system. `connect_portfolio`, `import_holdings`, and `import_transactions` are the three exceptions: a real implementation of any of them means authenticating against a real broker or depository, which means a live external credential (an API key, an OAuth client secret, a real brokerage/DMAT account) this project does not have and this pass cannot obtain on its own. This is exactly the standing exception this project's own process (`loop.md`'s operating-mode instruction) carves out: "anything requiring a live external credential you don't have... Status Proposed, document the real options, inject a placeholder/interface so the rest of the system can be built and tested around the gap." ADR-0021 is the direct precedent and template for how this project has already handled the same shape of gap for Agent Runtime's LLM provider.

No prior ADR, design artifact, or entry in `checkpoint.md` has ever named a specific broker or data-aggregator API for this project. `Thoughts.md` and the Implementation Plan describe Portfolio -> Portfolio State as a capability, never a vendor. The gap was not skipped by a previous pass; it was never reached, because User & Portfolio was whiteboard-only until this pass, and the placeholder (ADR-0022's `PlaceholderBrokerConnector`) is what makes it possible to build and test the rest of the component today without that decision being made first.

## Decision

**Upstox is the first and currently only supported broker integration; Zerodha and Groww remain named-but-undecided future options, to be added as additional `Default*` implementations behind the same `BrokerConnector` Protocol (ADR-0022).** Ship `DefaultUpstoxBrokerConnector` (`src/components/c01_user_portfolio.py`) as the real implementation behind the `BrokerConnector` Protocol that ADR-0022 defines. `connect()` / `exchange_auth_code()` establishes a real OAuth session against `https://api.upstox.com`; `fetch_holdings()` reads Upstox's long-term-holdings endpoint; `fetch_transactions()` reads the charges/historical-trades endpoints. The previous interim (`PlaceholderBrokerConnector`) is retained as a still-tested double for unit/integration work but is no longer the default wired into `DefaultUserPortfolio` in any production path.

This decision settles the "interim" half of this ADR's original name. Zerodha (Kite Connect) and Groww remain real, viable future options from the original Alternatives block and are explicitly **not** decided here — they are named-but-undecided, to be added later as additional `Default*BrokerConnector` implementations (`DefaultZerodhaBrokerConnector`, `DefaultGrowwBrokerConnector`) registered alongside `DefaultUpstoxBrokerConnector` against the same `BrokerConnector` Protocol ADR-0022 defined, with no change to `DefaultUserPortfolio`'s call sites. Picking the broker-agnostic `BrokerConnector` Protocol first (ADR-0022) and the concrete first implementation second (this ADR) is the order that makes that future addition a small, additive change rather than a redesign.

Given this is a portfolio agent aimed at the Indian market context this project's other planning documents assume, Upstox is the concrete first pick; Zerodha and Groww are named as the next realistic candidates without being resolved on the user's behalf.

## Alternatives considered

- **Zerodha Kite Connect API.** India's most widely used retail broker API, well-documented, actively maintained, with a large existing developer ecosystem to draw on. Real considerations the user would need to weigh: it is a paid API in production (a recurring per-app subscription fee, not a free tier), it requires the end user to actually hold a Zerodha trading/demat account (so it cannot onboard a user who holds elsewhere), and it is scoped to Zerodha's own holdings only — a user with accounts spread across multiple brokers would still need something else to get a complete picture, which cuts against `track_portfolio_state`'s implicit promise of one coherent snapshot.
- **Upstox API.** A comparable Indian broker API with a free tier for personal/developer use, avoiding Kite Connect's mandatory subscription cost. Same single-broker scoping problem as Kite Connect — a user's Upstox holdings only, nothing else — and a smaller ecosystem/documentation base to build against. Not evaluated against this project's specific needs (holdings + transactions + a stable session model for repeated `synchronize_portfolio` calls) any more than Kite Connect was; that evaluation hasn't happened for either.
- **RBI Account Aggregator (AA) framework** (e.g. accessed via a licensed intermediary such as Setu AA, Finvu, or Perfios's AA gateway, rather than talking to the RBI framework directly). A consent-based, multi-institution data-sharing framework that is not scoped to one broker — a single integration could in principle surface holdings/transactions across whichever of a user's financial institutions are AA-participating, which is a closer match to what `track_portfolio_state` implies than either single-broker option above. Real considerations: this is a materially heavier integration than a single broker's REST API — it requires becoming, or integrating through, a licensed Financial Information User (FIU), building a real user-consent flow (the AA framework's core mechanism), and depending on which of a user's institutions have actually onboarded as Financial Information Providers (FIPs) in the AA network, which is not universal coverage today. Higher integration and compliance cost, but the only option of the three that doesn't structurally lock a user into a single broker.

None of these is picked here. The real considerations — recurring cost (Kite Connect) vs. free tier with a smaller ecosystem (Upstox) vs. multi-broker coverage at a real compliance/integration cost (Account Aggregator), and whether single-broker scope is even acceptable given what `track_portfolio_state` is meant to represent — are named so the user has them, not resolved on the user's behalf.

## Consequences

- **Upstox's public sandbox (`sandbox.upstox.com`) is documented as covering ONLY order placement/modify/cancel and does not appear to cover the long-term-holdings or charges/historical-trades read endpoints this feature needs, so there is no sandbox path to validate the real read flow end-to-end before a live account exists.** Correctness of parsing/mapping/import is therefore established only against hand-authored fixtures matching the real documented response shapes (`tests/fixtures/upstox/long_term_holdings_empty.json`, `tests/fixtures/upstox/long_term_holdings_success.json`, etc.), exercised by the story-level QA tests in `tests/components/test_qa_story14_import_holdings.py`, `tests/test_qa_story19_broker_import.py`, and the related `tests/test_story5_*` / `tests/test_story23_*` suites. A real-account manual validation runbook at `../docs/runbooks/upstox-live-validation.md` records the explicit follow-up: a human runs the connect → import flow against one small real Upstox account, spot-checks the imported rows against the Upstox web portal, and then revokes/disconnects. That runbook is out-of-pipeline by design; the automated test suite must never call the real or sandbox Upstox API.
- **We take on an external credential dependency (`UPSTOX_CLIENT_ID` / `UPSTOX_CLIENT_SECRET` / `UPSTOX_REDIRECT_URI`) of the same shape as `OPENROUTER_API_KEY` / `ALPHA_VANTAGE_API_KEY`.** These are real secrets required by `UpstoxConfig.from_env()` (`src/upstox_config.py`) and documented in `.env.example`; they must be provisioned in the deployment environment before `connect_portfolio` will work against a real account. The `BROKER_TOKEN_ENCRYPTION_KEY` documented alongside them in `.env.example` is a separate dependency owned by `src/broker_token_crypto.py` for encrypting issued access tokens at rest — it has no third-party counterpart in this project's other external integrations and is a real additional secret this decision introduces. The same operational hygiene that applies to `OPENROUTER_API_KEY` / `ALPHA_VANTAGE_API_KEY` (no commit, rotate on personnel change, scoped env files) applies here.
- **Transaction history depth is bounded by Upstox to the last 3 financial years.** `import_transactions` cannot surface trades older than that, regardless of the date range passed in. This is a hard upstream limit, not a connector bug; users with longer history will see a partial view of their own portfolio through this integration and that gap is structural, not fixable inside `DefaultUpstoxBrokerConnector`.
- **A future Zerodha (Kite Connect) or Groww implementation lands behind the same `BrokerConnector` Protocol as an additive change.** `DefaultUserPortfolio`'s call sites do not change shape for that swap; the broker registry in `src/components/c01_user_portfolio.py` is already keyed by `broker_id` so a second `DefaultZerodhaBrokerConnector` / `DefaultGrowwBrokerConnector` is a new file plus a new registry entry, not a refactor. Picking the Protocol first (ADR-0022) and the concrete first implementation second (this ADR) is what makes that future addition a small change rather than a redesign.
- (Carried forward from the prior `Proposed` text.) This ADR is scoped to User & Portfolio's broker connection only. It says nothing about whether Data & Sources (component 02, still whiteboard-only) should use the same API, a different one, or something entirely unrelated (market data feeds are a different kind of external dependency than a user's own brokerage holdings) — that is a separate decision, not settled here.

## Open questions (still open at acceptance, not silently resolved)

The following three questions are **explicitly left open** by this ADR. They are recorded here so they are not silently decided, and each one names the current best-effort behaviour so a future reader knows what the system is doing in the meantime:

1. **Upstox rate limits are undocumented in any source we can verify.** The retry policy implemented in `_UpstoxHttp` (`src/upstox_http.py`) is a conservative guess (small per-request timeout, exponential backoff with bounded attempts, fail-fast on `4xx` other than `429`). It is not validated against any documented Upstox quota, and the manual runbook at `../docs/runbooks/upstox-live-validation.md` does not attempt to characterize the real limits either. A future pass that hits a real Upstox rate limit (e.g. `429` with a `Retry-After` header we currently ignore, or a per-minute burst cap) is the trigger to revisit this; until then, "conservative guess" is the honest answer, not "documented limit".
2. **Whether the token response includes `expires_in` / `refresh_token` is not answerable from any Upstox surface we have access to.** `DefaultUpstoxBrokerConnector.exchange_auth_code` therefore handles both fields as **absent**: it stores the raw access token, does not schedule a refresh, and relies on the next call to fail with `401`/`403` if the token has expired. If a future real-account runbook walk-through observes Upstox actually returning `expires_in` and/or `refresh_token`, that is a finding to record in `../checkpoint.md` and raise as a follow-up — it is **not** permission to silently flip the connector's branch on the basis of one manual run.
3. **Whether a background/async import job is needed is unknown until real portfolio sizes are known.** Today, `import_holdings` / `import_transactions` are synchronous request/response against the connector; the connector is synchronous against Upstox's HTTP. If a real account turns out to have thousands of trades spanning the 3-year window (Consequence #3), a synchronous import may exceed the webapp request budget and a background job becomes necessary. If real accounts stay small, the synchronous path is fine and a background job is over-engineering. The honest current state is "we don't know yet" — this runbook's manual validation against a small real account (§5 of `../docs/runbooks/upstox-live-validation.md`) is one data point but is not sufficient to decide.
