# 0039 — Interaction & Notification real mechanism: decision-dict contract, DecisionPolicy-delegated scoring, prioritize/personalize rules, and a real pending-feedback/response mechanism

**Status:** Accepted — 2026-08-26
**Component:** Interaction & Notification (13)

## Context

`src/components/c13_interaction_notification.py` was whiteboard-only before this pass — `InteractionNotification(Protocol)` and `StubInteractionNotification` only, no low-level design, no ADR. Its Protocol already fixes every method's signature (`generate_notification(decision: dict) -> Notification`, `prioritize_notification(notification: Notification) -> str`, `personalize_notification(notification: Notification, user: dict) -> Notification`, `deliver_notification(notification: Notification) -> bool`, `explain_decision(decision: dict) -> str`, `collect_feedback(notification: Notification) -> UserFeedback`, `collect_user_response(notification: Notification) -> dict`) and the original three-field `Notification(user_id, content, priority)`/`UserFeedback(notification_id, response)` dataclasses — neither Protocol changed by this pass.

Read Decision & Policy (12) first, as instructed. `DefaultDecisionPolicy` (ADR-0038) produces a `Decision(verified_claim: dict, actionability: str)` and separately exposes real `assess_significance(verified_claim)`/`assess_risk(verified_claim)` methods this component needs but must not reinvent. Read User & Portfolio (01) next: `User.preferences` is a plain `dict` — no `Preference` dataclass exists anywhere in this project, confirmed by search — so "real Preference data" means reading real keys off that dict. Read `DefaultDecisionPolicy.request_approval` and ADR-0038's "honestly incomplete pending a UI" pattern last: this component has an analogous gap for `collect_feedback`/`collect_user_response` (no UI or notification-and-wait mechanism exists anywhere in this project), and per this round's operating-mode instruction, that gap gets the same honest-real-mechanism treatment as `request_approval`, not ADR-0021's non-cognitive-placeholder treatment — it needs no LLM and no external credential, only a UI that doesn't exist yet.

Per this round's operating-mode instruction, every gap below is resolved here with documented engineering judgment (Status: Accepted) rather than left open, except the one narrow, genuine external-credential piece — which live email/SMS/push service backs `deliver_notification` — covered separately in ADR-0040 (Status: Proposed, ADR-0021's exact template).

## Decision

**The `decision: dict` contract — the shape `generate_notification` and `explain_decision` both read, defined here since neither the Protocol nor ADR-0038 fixed it:**

```
{
  "verified_claim": dict,   # ADR-0038's own verified_claim contract, unchanged
  "actionability": str,     # "notify" | "escalate" | "suppress"
  "user_id": str,           # the notification's recipient; Decision itself carries no such field
}
```

`Decision(verified_claim, actionability)` (component 12) has no recipient identity anywhere on it, and no prior ADR names how one reaches this component. Resolved here as an `asdict(Decision(...))` plus one additional `"user_id"` key the caller is expected to attach — the same kind of "the caller bundles what it has on hand" convention ADR-0038 itself used for `assess_relevance`'s `portfolio: dict` parameter. Every key read defensively (`.get(key, <default>)`), the same "honest miss, not a forced guess" posture every prior component's real implementation already uses.

**`Notification` gains four fields beyond its original three** (`id`, `actionability`, `significance`, `channel`, all defaulting so `StubInteractionNotification`'s existing three-argument construction stays valid untouched): `id` because nothing downstream (`deliver_notification`, `collect_feedback`, `collect_user_response`, the `Interaction` record) can reference a notification without a stable identifier, and none existed; `actionability`/`significance` because `prioritize_notification`'s signature takes only a `Notification` — no `Decision` — and its own instructions require a real, rule-based decision from those two signals, so they have to live somewhere reachable from that one argument; `channel` because `personalize_notification` needs somewhere to record which delivery channel a user's preferences selected, for `deliver_notification`'s injected `NotificationChannel` to read later. This is the "real, judged extension" the task's own brief invited when `Notification`'s original shape didn't carry enough — documented here rather than silently added.

**Three new dataclasses**, each real and used, not decorative: `Alert` (an escalation-specific companion record `generate_notification` raises and persists via `Infrastructure`/`AuditManager` whenever `actionability == "escalate"` — a durable, queryable trail distinct from an ordinary notification, matching `DefaultDecisionPolicy.escalate`'s own precedent of treating escalation as an audit-relevant event); `Explanation` (the structured intermediate `explain_decision` assembles — claim, actionability, relevance, significance, risk, rationale — before rendering it through the one fixed template `_render_explanation` documents, so the real numbers behind an explanation are named once rather than scattered across an f-string); `Interaction` (the notify-to-respond lifecycle record `collect_feedback`/`collect_user_response` persist and update, one row per `Notification.id` — the hand-off artifact the module's own docstring already names as flowing `-> Learning & Evaluation (14)`).

**`generate_notification`/`explain_decision`: both delegate significance/risk to the injected `DecisionPolicy` (`DefaultDecisionPolicy` by default) via a shared private `_score_decision` helper, never reimplementing ADR-0038's weighted formulas.** This mirrors ADR-0038's own precedent of delegating relevance to `UserPortfolio` rather than reinventing exposure math inside Decision & Policy — the same "call the real component that owns this computation" discipline, one layer further down the pipeline. `generate_notification` builds `Notification.content` from the claim text, confidence, actionability, and entity id (all real fields off `verified_claim`), and raises an `Alert` when the decision escalates. `explain_decision` builds an `Explanation` from the same real relevance/significance/risk numbers and a qualitative `rationale` keyed only on `actionability` (via `_rationale_for`) — deliberately not re-deriving ADR-0038's own numeric thresholds a second time in this component, keeping component 12 the single source of truth for where the notify/escalate/suppress lines actually sit. The rendered string is genuinely templated, structured prose over real numbers — never free-form generation.

**`prioritize_notification`: real, rule-based on `notification.actionability`/`notification.significance`** (the two fields this ADR added to `Notification` above, populated by `generate_notification`). Escalations are always `"critical"`; among `"notify"` decisions, a `_PRIORITY_HIGH_SIGNIFICANCE_THRESHOLD = 0.5` splits `"high"` from `"normal"`; anything else is `"low"`. This is this component's own sub-priority split within what Decision & Policy already classified as `"notify"` — distinct from, not a restatement of, ADR-0038's escalate/notify/suppress thresholds. Mutates `notification.priority` in place before returning it, the same pattern `DefaultDecisionPolicy.determine_actionability` already established for its own `Decision` argument.

**`personalize_notification`: real, reads `user["preferences"]`** (a plain dict, per User & Portfolio's own `User.preferences` shape — no `Preference` dataclass exists to import). Three documented rules: `preferences.get("id", ...)` — actually `user.get("id", ...)` — replaces `notification.user_id` rather than trusting the value already on the input, the same "never trust a possibly-stale caller value" posture `DefaultUserPortfolio.manage_preferences` already established; `preferences.get("notification_channel", ...)` selects `notification.channel`; `preferences.get("notification_verbosity") == "detailed"` appends a pointer to `explain_decision`; `preferences.get("quiet_mode")` downgrades priority to `"low"` for anything short of an escalation, and never for one — quiet hours are a real personalization, not a bypass of a genuine risk escalation. Returns a new `Notification` rather than mutating the input, since every recipient-specific field is rebuilt fully from `user`, not incrementally.

**`deliver_notification`: calls through an injectable `NotificationChannel` Protocol** (`send(notification) -> bool`), default `PlaceholderNotificationChannel` (ADR-0040), and records the outcome via `AuditManager` (`"notification_delivered"` or `"notification_delivery_failed"`) — the task's own suggestion that `DefaultAuditManager` is worth using here, adopted because a delivery attempt and its outcome are exactly the class of event this project's other components already treat as audit-relevant (`DefaultDecisionPolicy.escalate`, `enforce_policy`'s rate-limit blocks).

**`collect_feedback`/`collect_user_response`: real, honest pending-mechanism, `DefaultDecisionPolicy.request_approval`'s exact template applied here.** Both persist/read a real `Interaction` row via `Infrastructure` (`_get_or_create_interaction`, idempotent by `notification.id` — a repeated call before anything external has answered finds the same pending row rather than creating a duplicate, the same idempotency posture `request_approval` already established for its own per-action-id rows). If the stored row already carries real `feedback`/`response` content, that's returned; otherwise a pending row is created (or reused), an `AuditManager` event is recorded (`"feedback_requested"`/`"response_requested"`), and an honest `{"status": "pending", ...}` is returned. Nothing external can write real feedback or response content onto that row yet — there is no UI, no feedback form, no channel that answers back — stated plainly here and in both methods' docstrings, not disguised as a working round trip.

## Alternatives considered

- **Adding a `portfolio`/`user` parameter to `generate_notification`/`explain_decision` so relevance could be recomputed fresh instead of read off `verified_claim`.** Rejected — the Protocol already fixes both signatures to take only `decision: dict`; changing them would be an unauthorized signature change, not a real gap this pass is free to resolve. `verified_claim["relevance"]` is already the real, caller-attached value per ADR-0038's own contract; reading it is not a shortcut, it's the contract as designed.
- **Recomputing ADR-0038's own significance/risk thresholds inside `_rationale_for` to explain exactly why a decision landed where it did (e.g. "risk 0.62 exceeded the 0.60 escalate threshold").** Rejected as a duplicated source of truth — component 12 already owns those threshold values; hardcoding them a second time here would silently create two places that could drift apart. `_rationale_for` reads only the `actionability` string component 12 already computed.
- **Passing `Decision` (component 12's dataclass) directly instead of a `decision: dict`.** Rejected — the Protocol already fixes the parameter type to `dict`, matching `assess_relevance`'s own `portfolio: dict` convention rather than importing a typed dataclass across a component boundary; changing it would again be an unauthorized signature change.
- **Giving `NotificationChannel.send` a `**kwargs` "extra context" escape hatch instead of taking the full `Notification`.** Rejected — `Notification` after this ADR's field additions already carries everything a real channel implementation would need (recipient, content, channel selection, priority); an extra untyped parameter would just be unused surface area today.
- **Treating `collect_feedback`/`collect_user_response` as a `Proposed` placeholder ADR, ADR-0021's template.** Rejected per the task's own explicit instruction, matching ADR-0038's own reasoning for `request_approval`: this is not a reasoning/external-credential gap (no LLM, no third-party API is needed to persist a pending record and check its status) — it is a real mechanism this pass can and does build, honestly incomplete only in that nothing external can answer yet.

## Consequences

- `Notification`'s `actionability`/`significance`/`channel`/`id` fields only carry real values when populated by `generate_notification`/`personalize_notification` in this component's own pipeline — a `Notification` constructed directly by a caller that skips those steps (e.g. a test building one by hand) will have `actionability=""`/`significance=0.0`, and `prioritize_notification` will correctly fall through to `"low"` rather than guessing.
- `explain_decision`'s `rationale` text is coupled to component 12's three-way actionability outcome by name (`"escalate"`/`"notify"`/`"suppress"`) — if ADR-0038 ever adds a fourth outcome, `_rationale_for`'s fallback (`"actionability not yet determined"`) will fire for it until this component is revisited, rather than crashing.
- `collect_feedback`/`collect_user_response`'s `Interaction` rows can never be seen or answered by a real person today — there is no UI, no feedback form, no response channel anywhere in this project. Anything that depends on feedback or a response actually arriving is not yet safe to build on top of this method; it is safe to build on top of its pending-state bookkeeping and idempotency being real, exactly as ADR-0038 already stated for its own `request_approval`.
- `deliver_notification` is never really delivering anything today (ADR-0040) — every call returns `False` and every attempt is logged as a failure. Any caller treating a `True` return as proof of delivery would be wrong to; nothing in this project can produce `True` from `PlaceholderNotificationChannel` by design.
- The `decision: dict` contract's `"user_id"` key is now the de facto hand-off point between Decision & Policy (12) and Interaction & Notification (13) for recipient identity — if a future pass gives `Decision` its own recipient field instead, this component's `generate_notification`/`explain_decision` need to be revisited alongside that change.
