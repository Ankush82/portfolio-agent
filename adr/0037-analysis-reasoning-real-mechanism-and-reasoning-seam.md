# 0037 — Analysis & Reasoning real mechanism: fan-in orchestration, Evidence & Verification-backed hypothesis testing, and injected reasoning seam

**Status:** Accepted — 2026-08-26
**Component:** Analysis & Reasoning (08)

## Context

`src/components/c08_analysis_reasoning.py` was whiteboard-only before this pass — `AnalysisReasoning(Protocol)` and `StubAnalysisReasoning` only, no low-level design, no ADR. Its nine capabilities (`analyze`, `compare`, `infer`, `generate_hypotheses`, `test_hypotheses`, `estimate_impact`, `generate_explanations`, `generate_counterarguments`, `synthesize_findings`) are this project's first component whose *entire job* is inference and synthesis, not orchestration with an inference step bolted on. Every other component implemented so far this session (Event & Observation/07, Retrieval & Context/05, Evidence & Verification/09, Knowledge & Entity/04, Data Processing & Quality/03) found a real, honest, rule-based or statistical substitute for what looked like it might need cognition — a z-score threshold, a keyword rule, a Jaccard-overlap gate, edit-distance fuzzy matching. None of those substitutes generalize to "what does this evidence suggest," "what else could explain this," or "how significant is this really" — there is no honest structural stand-in for hypothesis generation the way there was for anomaly detection.

The Protocol's own docstring on `analyze` already names the shape: "Converges Event, Observations, Context, Memory, and Evidence into one step — see the Component Whiteboards fan-in figure." Reading the four now-real components this one is supposed to converge, as instructed: `DefaultEventObservation` (07, ADR-0036) exposes real `retrieve_events(filters) -> list[Event]`, statistically/rule-based, `Infrastructure`-backed; `DefaultMemoryManager` (06, ADR-0005) exposes real `retrieve(query: dict, scope: str) -> list[Memory]` against a bounded working set; `DefaultContextBuilder` (05, ADR-0033) exposes real `construct(documents, query=None) -> ContextPack` backed by a real sufficiency evaluator; `DefaultEvidenceLinker`/`DefaultClaimVerifier`/`DefaultMandatoryEvidenceGate` (09, ADR-0029/0030/0031/0013) expose a complete, real evidence-linking-and-verification pipeline over a `Claim(text, source_component)`; and `DefaultUserPortfolio.calculate_exposure` (01) exposes real portfolio exposure by security given a `PortfolioSnapshot`. None of this is a lookup or a threshold check to *use* — assembling these real inputs into what an analysis needs, running a tested hypothesis through Evidence & Verification's real pipeline, and doing a structural diff between two dicts are all real, mechanical orchestration; deciding what to infer from them, what to hypothesize, what to conclude, and how significant it is are not.

This is the same root cause ADR-0021 already named for Agent Runtime's `reason`/`assess_stakes`: no ADR, no document in this project, has ever chosen an LLM provider. That gap is not re-litigated here — restated only insofar as this component depends on the same still-open decision.

Per this round's operating-mode instruction, every part of this component that has a real, computable answer is decided and implemented here (Status: Accepted) rather than left open; only the genuinely cognitive parts get the injectable-placeholder treatment, following ADR-0021's exact pattern rather than inventing a second one.

## Decision

**`analyze`, `compare`, `test_hypotheses`: real orchestration, no `reason_fn` involved.**

- `compare(a, b)` is a genuine structural diff over two given dicts: `only_in_a`/`only_in_b` for keys unique to one side, `changed` for every shared key whose values differ (`{"a": ..., "b": ...}`). No cognition needed to compare two dicts structurally.
- `test_hypotheses(hypotheses)` is a real, complete hand-off to Evidence & Verification (09): a `Hypothesis` becomes a `Claim` via `claim.text = hypothesis.claim`, `claim.source_component = "Analysis & Reasoning"` — the shapes line up exactly, no adapter needed beyond that one-field mapping. Each claim is linked against real evidence (`EvidenceLinker.link`), gated by `MandatoryEvidenceGate.has_evidence` (ADR-0013's mandatory-per-claim rule), and — only if it clears the gate — verified for real (`ClaimVerifier.verify`, ADR-0031's citation-completeness/confidence formula). A hypothesis with no linkable evidence is blocked (`gate.block`, which records the block via `AuditManager`) and **dropped from the returned list** — the same "logged, not forwarded" posture ADR-0013 already established for any other unevidenced claim, not silently passed through with a low score. A hypothesis that clears the gate keeps its original `basis` dict, extended (not replaced) with `verified: True`, `confidence`, `evidence_count`, `was_contradictory` — so whatever `generate_hypotheses` already attached survives alongside the real verification result.
- `analyze(event, context, memory)` does the fan-in the Protocol's own docstring describes, via a private `_gather_analysis_input` helper that is itself pure real orchestration: `event["entity_ids"]` (or a single `event["entity_id"]`) drives real `EventObservation.retrieve_events({"entity_id": ...})` calls to find correlated historical events; `memory` (already dict-shaped exactly like `MemoryManager.retrieve`'s own `query` parameter) is passed straight through to `retrieve(memory, scope)` for every configured scope (`"user"`, `"shared"` by default); `context["documents"]` and `context["query_text"]` build a real `Query`, passed to `ContextBuilder.construct` for a real, evaluator-backed `ContextPack`; and when the caller attaches a `PortfolioSnapshot` at `context["portfolio_snapshot"]`, `UserPortfolio.calculate_exposure` computes real exposure. `analyze` then composes: gather (real) -> `generate_hypotheses` (cognitive) -> `test_hypotheses` (real) -> `synthesize_findings` (cognitive, and where the resulting `Analysis` is persisted — see below).

**`infer`, `generate_hypotheses`, `generate_explanations`, `generate_counterarguments`, `synthesize_findings`: behind an injected `reason_fn: Callable[[dict], dict]`**, same shape and spirit as `build_agent_runtime_graph`'s `reason_fn` (`c10_agent_runtime.py`, ADR-0021). Each method sends a `{"phase": ..., ...}` request and interprets the response into its own real return type (`Hypothesis`, `list[Hypothesis]`, `str`, `list[str]`, `Analysis`) — that interpretation and type conversion is itself mechanical, not cognitive; only the content of the answer requires judgment. `placeholder_reason_fn` (this component's own, not a reuse of Agent Runtime's) ships as the default: it inspects nothing about its input and returns a fixed, low-confidence, explicitly-labeled non-answer per phase — a single "insufficient basis to hypothesize" `Hypothesis` for `infer`, an empty list/string for every method that returns a collection, `{"significance": "unknown", ...}` for `estimate_impact`'s judgment half.

**`estimate_impact`: split down the middle, not forced entirely behind the placeholder.** The real half — actual portfolio exposure to whatever entity `hypothesis.basis["entity_id"]` references, computed via `UserPortfolio.calculate_exposure` against `hypothesis.basis["portfolio_snapshot"]` when the caller attached one — runs first and unconditionally, real whether or not `reason_fn` is a placeholder. The judgment half — how significant the underlying event actually is — goes through `reason_fn` and is merged into the same returned dict (`{"exposure": ..., **judgment}`). This is the one method in the component where part of the answer is genuinely computable today and part genuinely is not; splitting it, rather than gating the whole method behind `reason_fn`, is a deliberate choice to not throw away a real, available answer just because a different part of the same method needs judgment.

**Persistence: `synthesize_findings` persists the final `Analysis` via `Infrastructure` (ADR-0019), nothing else does.** A new `"analyses"` table (`{"id", "hypotheses", "impact_estimate", "synthesized_at"}`) records every synthesized `Analysis` — the durable output of this component's pipeline. Intermediate `Hypothesis` objects generated by `generate_hypotheses` or tested by `test_hypotheses` are not separately persisted; they have no natural identity of their own until synthesis picks a final set, and persisting every intermediate would flood the table with routine, superseded values the same way ADR-0036 argued against auditing every routine `Change`. This mirrors `DefaultRetriever`'s own choice (ADR-0033) to log at its real output boundary, not every intermediate step.

## Alternatives considered

- **Writing `infer`/`generate_hypotheses`/etc. as keyword-matching or template-filling functions and calling them real inference.** Rejected outright, per this task's own explicit instruction: a keyword match dressed up as `infer` would be indistinguishable from real reasoning to a caller, which is a worse property than an honestly-labeled placeholder that cannot be mistaken for one. Every other component in this project earned its "real, no LLM" claim with a defensible, named rule (a z-score, an edit-distance threshold); no such defensible rule exists for "what should I hypothesize from this evidence."
- **A single shared `reason_fn` module-level default reused from `c10_agent_runtime.py`.** Rejected — the task explicitly calls for "one `placeholder_reason_fn` for this component specifically." The request/response shapes genuinely differ (Agent Runtime's `reason_fn` speaks `{"phase": "reason"/"assess_stakes"}`; this component's speaks `{"phase": "infer"/"generate_hypotheses"/...}`), so sharing one function would mean one of the two components silently ignoring phases it doesn't recognize, or a combined function neither ADR fully owns. Two separate, ADR-documented placeholders, one per component, keeps each one's contract legible on its own.
- **Forcing all of `estimate_impact` behind `reason_fn`, including the exposure computation.** Rejected per this task's explicit instruction not to force a whole method behind the placeholder when part of it has a real, computable answer — `UserPortfolio.calculate_exposure` already exists and is real; refusing to call it here would throw away a genuinely available number for no reason beyond method-level tidiness.
- **`test_hypotheses` returning every hypothesis with a `blocked: True` flag instead of dropping unevidenced ones.** Rejected — ADR-0013 is explicit that an unevidenced claim is "logged, not forwarded, not passed through down-weighted." A flagged-but-still-returned hypothesis is exactly the down-weighted-pass-through ADR-0013 already ruled out for claims generally; there is no reason a hypothesis (which becomes a claim for this exact check) should get gentler treatment.
- **Giving `_gather_analysis_input` its own public Protocol method** (a fourth "real" capability beyond `analyze`/`compare`/`test_hypotheses`). Rejected — the `AnalysisReasoning` Protocol's signature is fixed at nine methods; `analyze` is already the one place the fan-in is documented to happen, so its real gathering logic lives as a private implementation detail of `analyze` itself, not a tenth public surface nothing calls independently.

## Consequences

- Nothing `generate_hypotheses`/`infer`/`generate_explanations`/`generate_counterarguments`/`synthesize_findings` produce right now is a real hypothesis, inference, explanation, counterargument, or synthesis — with `placeholder_reason_fn` behind them, `analyze()`'s own output is, honestly, always an empty `Analysis` today, because `generate_hypotheses` returns nothing for `test_hypotheses` to test and `synthesize_findings` returns nothing to persist. The orchestration around it — the real fan-in gathering, the real evidence-linking-and-verification pipeline `test_hypotheses` runs when it does have hypotheses to test, the real exposure computation in `estimate_impact` — is independently correct and testable today; anything that depends on this component actually inferring, hypothesizing, or concluding something is not yet safe to build on top of this implementation, same posture ADR-0021 already stated for Agent Runtime's reasoning.
- Once an LLM provider is chosen (ADR-0021's still-open decision), the fix here is narrowly scoped the same way: implement a real `reason_fn` matching this component's own six phases (`infer`, `generate_hypotheses`, `generate_explanations`, `generate_counterarguments`, `synthesize_findings`, `estimate_impact`) and pass it into `DefaultAnalysisReasoning`'s constructor instead of `placeholder_reason_fn`. No method's real-orchestration half needs to change for that swap — `test_hypotheses`'s Evidence & Verification integration, `analyze`'s fan-in gathering, and `estimate_impact`'s exposure computation are all real today and stay real afterward.
- `test_hypotheses`'s real dependency on Evidence & Verification means this component's own hypothesis-testing quality is only as good as `DefaultEvidenceLinker`'s Jaccard-token-overlap linking and `DefaultClaimVerifier`'s structural confidence scoring (ADR-0029/0030/0031) — both of which are themselves honest heuristics, not semantic matching, pending the same LLM/embedding-provider decision (ADR-0028/ADR-0021). A hypothesis whose wording shares little vocabulary with genuinely-relevant memory or context content can be blocked for lack of *findable* evidence even when relevant evidence technically exists — a real, inherited limitation, not new to this component.
- `synthesize_findings`'s persistence to `"analyses"` stores whatever `reason_fn` hands back verbatim (via `dataclasses.asdict` on each `Hypothesis`); a future real `reason_fn` that attaches non-JSON-serializable objects into a `Hypothesis.basis` (e.g. a raw `PortfolioSnapshot` instead of its own fields) would need to keep that content serializable for `DefaultInfrastructure`'s real Postgres backing — not a concern today since `placeholder_reason_fn` never attaches complex objects, but worth flagging for whoever writes the real `reason_fn`.
