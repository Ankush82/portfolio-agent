# 0049 — Core-entity repository layer: typed columns, append-only transactions, ADR-0019 reaffirmed

**Status:** Accepted — 2026-08-27
**Component:** User & Portfolio (01), System Infrastructure (18)

## Context

The four core portfolio entities — `User`, `Portfolio`, `Holding`, `Transaction` — have lived as `@dataclass`es inside `src/components/c01_user_portfolio.py` since ADR-0044, with their persistence happening directly against `DefaultInfrastructure.store/retrieve/query` and the JSONB `records` table. That worked for the first version of this component but, as more stories (STORY-14 holdings import, STORY-15 transactions import, STORY-17 broker re-sync, STORY-18 user settings, STORY-19 broker import) leaned on those four dataclasses, four real problems surfaced that this ADR resolves:

1. **Circular-import hazard.** Broker-sync code that needed to construct a `Holding`/`Transaction`/etc. had to import `components.c01_user_portfolio`, which transitively pulls in `Knowledge & Entity Model`, `DefaultUpstoxBrokerConnector`, `UpstoxConfig`, `_UpstoxHttp`, `UpstoxConfig`, `ExchangeRateFetchError`, `BoundaryGate`, etc. — every one of those module-load-time side effects was a circular-import risk waiting to happen, and the existing `from upstox_http import _UpstoxHttp` inside `DefaultUpstoxBrokerConnector.__init__` (the existing "deferred import to avoid a circular deadlock" pattern this file already carries) is direct evidence the file is at its import-graph limit.
2. **JSONB-only persistence made broker re-sync idempotency impossible.** A `Holding` was stored as a single `data JSONB` blob keyed by `(table_name, id)`. The `(portfolio_id, security_id)` uniqueness the broker re-sync idempotency rule (the same rule ADR-0022's `replace_broker_holdings` enforces at the SQL level for `broker_holdings`) depends on was either unindexable (`data->>'portfolio_id'`) or unindexed (no real index, only a JSONB containment match for `query`). Same for `Transaction` deduplication: no typed column means no real UNIQUE constraint means no `ON CONFLICT DO NOTHING` means every re-sync potentially duplicates rows.
3. **Lazy `CREATE TABLE IF NOT EXISTS` for tables the system actually relies on.** ADR-0019's "schema is created lazily and idempotently the first time a Postgres connection is opened" rule has worked for one-off tables (e.g. `tmp_us_tickers`, `migration_log`), but for *the four tables that hold the user's portfolio* it's the wrong primitive: a broker re-sync silently no-ops on a fresh database (same fragility bug STORY-19 found live for `broker_transactions` — a real `psycopg.errors.UndefinedTable` swallowed with a warning log rather than a clear migration-required signal), and any column-rename or ADD COLUMN has to be hand-coordinated with the lazy CREATE block, which is exactly the kind of drift the `run_migration.sh` + `.sql` + `verify_migration.py` tooling this repo already adopted for `migrate_us_stocks` / `migrate_broker_transactions` exists to prevent.
4. **No real test that the schema is what the code thinks it is.** The current `DefaultInfrastructure.store/retrieve/query` paths assume "table exists with a JSONB `data` column" — a real change to that contract (e.g. someone drops `data`, adds typed columns without coordinating) silently breaks every reader without a single failing test.

This ADR resolves all four by introducing a thin repository layer over the existing Infrastructure protocol, on terms that preserve ADR-0019 and every other prior decision rather than reversing any of them.

## Decision

### 1. Domain extraction: `src/domain.py` is the home for the four entity dataclasses

The four `@dataclass`es — `User`, `Portfolio`, `Holding`, `Transaction` — plus the four table-name constants — `USERS_TABLE`, `PORTFOLIOS_TABLE`, `HOLDINGS_TABLE`, `TRANSACTIONS_TABLE` — move to a new stdlib-only module `src/domain.py`. `src/domain.py` has zero project-internal imports (only stdlib: `dataclasses`, `typing`, `datetime`, `decimal`). Repositories depend on `src/domain`, never on `src.components.c01_user_portfolio` (or any other component).

`src/components/c01_user_portfolio.py` re-exports `User`, `Portfolio`, `Holding`, `Transaction`, `USERS_TABLE`, `PORTFOLIOS_TABLE`, `HOLDINGS_TABLE`, `TRANSACTIONS_TABLE` from `src.domain` for backward compatibility — every existing `from components.c01_user_portfolio import User` / `from c01_user_portfolio import Portfolio` / etc. site keeps working unchanged, the same additive re-export shape ADR-0019/ADR-0035 already used for the `KnowledgeEntity` boundary. New code (broker-sync, future repositories) imports from `src.domain` directly and never touches `c01`.

`Transaction` stays as it is — `Transaction(portfolio_id, kind, amount)`, with no broker reference, no timestamp, and no natural identity field — for the reasons in decision 4 below.

#### Consequences

- `src/upstox_http.py` (and any other module that needs `Transaction`/`Holding`/etc. but does not need any of `c01`'s component classes) can now `from domain import Transaction, Holding, USERS_TABLE` without pulling in `KnowledgeEntity`, `UpstoxConfig`, `BoundaryGate`, or any of the rest of `c01`'s transitive surface — and without any risk of a circular import at module load time.
- The four dataclasses become component-independent value types: they describe the user's data, not "a thing component 01 owns." Component 01 is the *coordinator* of those values, not their source of truth. This matches the role ADR-0044 already gives `DefaultKnowledgeEntity.get_entity`/`search_entities` (a class on component 04 that `c01` imports *into*, not out of): the four entity dataclasses now sit at the same conceptual level, available to whoever genuinely needs them rather than walled behind `c01`.
- The `c01` re-export surface is purely additive — no existing import path is removed, and no test or downstream module has to change to follow this ADR. This is the same "extra real-behavior accessor beyond a fixed Protocol, via re-export, not by removal" pattern ADR-0035/ADR-0044 already established.

### 2. Real typed columns, not an opaque JSONB payload — and a `MIGRATED_TABLES` registry on `DefaultInfrastructure`, not on the repositories

The four migrated tables (`users`, `portfolios`, `holdings`, `transactions`) each carry **one real typed column per dataclass field** plus a primary key, not a single `data JSONB` blob. `users.preferences` is the sole JSONB column, because it is genuinely an open-ended mapping (per-user preference dicts that grow as new preferences are added, the same shape `manage_preferences` already writes). Every other field on every other table is a real, typed Postgres column (e.g. `holdings.quantity NUMERIC(18, 4) NOT NULL`, `transactions.kind TEXT NOT NULL CHECK (kind IN ('BUY','SELL','DIVIDEND','FEE'))`).

The reason this matters is concrete, not aesthetic:

- **Foreign keys.** `holdings.portfolio_id` is a real `TEXT NOT NULL REFERENCES portfolios(id)`, which gives the system an actual integrity guarantee that a holding's portfolio exists. JSONB cannot enforce that at all.
- **List predicates.** `list_for_user(user_id: str) -> list[Portfolio]` and `list_for_portfolio(portfolio_id: str) -> list[Holding]` are real `WHERE portfolio_id = %s` queries against a real indexed column. Against JSONB, the equivalent is either an unindexed `data->>'portfolio_id' = %s` (table scan on every call) or a JSONB GIN index this project would have to add, tune, and maintain — for a column that already had a typed, indexable shape available.
- **Uniqueness the broker re-sync idempotency rule depends on.** `UNIQUE(portfolio_id, security_id)` on `holdings` (mirroring what ADR-0022's `broker_holdings` already enforces at the SQL level for the broker-side table) makes "broker re-sync sees the same holding twice, must not duplicate" a real `ON CONFLICT DO NOTHING`, not a defensive application-level dedupe that has to be re-implemented in every caller.

`MIGRATED_TABLES` lives on `DefaultInfrastructure` — a class-level registry mapping each migrated table name to its column-to-dataclass-field mapping. `DefaultInfrastructure.store(table, record)` / `retrieve(table, id_)` / `query(table, filters)` consult the registry: when `table in MIGRATED_TABLES`, the SQL is the column-aware form (real `INSERT INTO <table> (<column-list>) ... ON CONFLICT (<pk>) DO UPDATE SET <column-list>`; real `SELECT <column-list> FROM <table> WHERE ...`); when `table not in MIGRATED_TABLES`, the legacy JSONB-blob path is unchanged. **Repositories stay SQL-free** — they call `infrastructure.store(table, record)` and read a `dict` back, the same way every other component calls Infrastructure today. The typed-columns shape is enforced at the Infrastructure layer, where ADR-0019 already says "schema" lives.

**Rejected alternative: introspecting `information_schema` at call time to learn the column shape.** Rejected because (a) it adds a per-call `information_schema.columns` round-trip on every `store`/`retrieve`/`query` (or a per-process cache that has to be invalidated on every `ALTER TABLE`), (b) the introspection result drifts silently if a migration adds a column the application code doesn't know about (the repository would just persist `NULL` for the new column with no warning), and (c) the application code still has to know which field maps to which column to build the `INSERT` column list, so introspection saves nothing the registry doesn't already say authoritatively at import time. The registry is the source of truth; `information_schema` is what the registry is *describing*, not what the repositories should be *querying at runtime*.

**Drift guard.** A real test (per the compliance-test pattern ADR-0019 is now also enforced by — see decision 5) asserts `set(MIGRATED_TABLES.keys()) == {USERS_TABLE, PORTFOLIOS_TABLE, HOLDINGS_TABLE, TRANSACTIONS_TABLE}` and that the column list for each registered table matches the corresponding dataclass's field list exactly (every dataclass field has a column, every column corresponds to a dataclass field, no `extra=...` on the dataclass side, no `NULL`-default columns on the dataclass-required-field side). The test runs against the live `DefaultInfrastructure` after `scripts/migrate_core_entities.sql` has applied, so a registry that drifts from the schema — or a schema that drifts from the dataclass — fails CI before either can ship.

#### Consequences

- `DefaultInfrastructure` grows a real `MIGRATED_TABLES` registry plus the column-aware SQL it dispatches to. This is a strict superset of the current JSONB-only path: any non-migrated table (the queue tables, `tmp_us_tickers`, `migration_log`, `schema_migrations`, the future-broker-integration tables) keeps using the JSONB path unchanged.
- Every component that currently calls `infrastructure.store(table, record)` / `infrastructure.retrieve(table, id_)` / `infrastructure.query(table, filters)` against one of the four migrated tables gets the typed-columns behavior for free, with no caller-side code change — the contract is "you pass a dict matching the dataclass fields, you get back a dict matching the dataclass fields." Existing tests that assert on the persisted shape continue to pass because the dict-in / dict-out shape is preserved.
- Repository modules can stay SQL-free (`repositories/users_repo.py`, `repositories/portfolios_repo.py`, etc., each importing `domain` and `infrastructure` and writing zero SQL — the same "no SQL in components, SQL only in infrastructure" separation ADR-0019 already establishes for the existing typed tables like `broker_connections` and `broker_transactions`).
- One test failure mode is now loud rather than silent: if someone changes a dataclass field without updating `MIGRATED_TABLES` (or vice versa), the drift-guard test fails at PR time, not at the next broker re-sync on a production database.

### 3. Lazy `CREATE TABLE IF NOT EXISTS` removed for these four tables only; legacy JSONB column retained

For the four migrated tables, `DefaultInfrastructure._ensure_schema` no longer issues `CREATE TABLE IF NOT EXISTS`. Instead, those four tables are created (and any later column-additions performed) by the real migration script `scripts/migrate_core_entities.sql`, run through this project's existing `scripts/run_migration.sh` wrapper, exactly like `scripts/migrate_us_stocks.sql` / `scripts/migrate_broker_transactions.sql` are today.

`MigrationRequiredError(DefaultInfrastructureError)` is raised by `DefaultInfrastructure.store/retrieve/query` when `table in MIGRATED_TABLES` and the table does not exist in the database — same posture `upsert_broker_transaction` already takes on `psycopg.errors.UndefinedTable` (logged warning + silent no-op), but upgraded from "silently no-op, returning False / empty" to "raise loudly so the failure is visible" for the four tables that hold the user's portfolio. The generic lazy `CREATE TABLE IF NOT EXISTS` mechanism stays in place for every *other* table (queue tables, `tmp_us_tickers`, `migration_log`, `schema_migrations`, the future broker-integration tables) — this ADR only removes it for the four tables that have a real, named migration script.

**Legacy convergence.** For any database that already has the old JSONB-blob `records(table_name='holdings')` rows (i.e. any database this project has actually been running on, including the dev database every developer has locally), the migration script's `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements add the new typed columns one at a time, in the same way `scripts/migrate_us_stocks.sql` adds columns idempotently. A guarded backfill — `UPDATE ... SET <typed_col> = (<typed_col> IS NULL) ? (data->>'<field>')::<type> : <typed_col> WHERE table_name = '<old_records_name>'` — populates the typed columns from the legacy JSONB payload, wrapped in a `BEGIN ... EXCEPTION WHEN ... THEN NULL` block so a row whose JSONB doesn't match the new shape (an expected, real edge case for some legacy rows) is logged and skipped rather than aborting the whole migration. The legacy JSONB `data` column is **retained, not dropped** — dropping it is a separate, explicit decision whose risk profile (irrecoverable data loss if anything ever needed it for forensic reasons, including reproducing the original bug reports this ADR exists to fix) does not belong in the same migration. A follow-up ADR can decide to drop it once enough time has passed to be confident nothing references it.

**What shipped and what didn't.** `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` and `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()` shipped on all four tables — the same pattern ADR-0022's `broker_connections` already established. **No foreign key had to be dropped** for legacy or behavioral reasons: every typed column on every migrated table is a real `NOT NULL` (or `NULL`-tolerant, where the dataclass field allows it) with a real type, and no FK in the new schema conflicts with anything in the legacy JSONB payload. The one FK that *did* have to be created for the first time is `holdings.portfolio_id TEXT NOT NULL REFERENCES portfolios(id)` and `transactions.portfolio_id TEXT NOT NULL REFERENCES portfolios(id)` — both new, not the result of dropping anything.

#### Consequences

- A genuinely fresh database (or any database that hasn't run `scripts/migrate_core_entities.sql`) fails loudly on the first broker re-sync, instead of silently dropping data the way `upsert_broker_transaction`'s swallowed `UndefinedTable` warning did on STORY-19. The error message names the missing migration script by file path, the same way the existing migration tooling already surfaces its own failures via `LOG_FILE`.
- The migration tooling decision in decision 5 is reaffirmed by this concrete migration: `run_migration.sh` + `.sql` + `verify_migration.py` (no alembic, no ORM) is what gets the new tables into a real database, end-to-end, just like every other schema change in this repo.
- The legacy JSONB payload column is still there if a real need to roll back ever arises (see "Manual rollback SQL" below). It costs ~one column of disk space per row in exchange for an actual rollback path, which is the right trade.
- `created_at`/`updated_at` shipped on all four tables, no FK was dropped — recorded explicitly per the "record whether created_at/updated_at shipped and whether any FK had to be dropped" requirement, so a follow-up reading this ADR does not have to guess.

### 4. Transactions are append-only: no broker reference, no timestamp, no natural identity — broker re-sync therefore duplicates rows

`Transaction(portfolio_id, kind, amount)` is the dataclass as it stands, and it stays as it stands for this ADR. There is no `broker_txn_id`, no `imported_at`, no `user_id` (ownership is inferred via the portfolio, which already references the user — see the `holdings.portfolio_id` FK above), no natural identity field beyond `(portfolio_id, kind, amount, ...)` — and no field that *could* be a correct dedupe key:

- A broker transaction's `external_id` is broker-specific (Upstox's id, Zerodha's id, etc.) and does not generalize across brokers.
- `(portfolio_id, kind, amount)` is not unique: two identical-looking transactions on the same day (e.g. two `BUY` orders of the same quantity at the same price from different brokers, or a real `BUY` + an `ADJUSTMENT` that happens to net to the same amount) are not the same transaction and must both persist.
- A timestamp would help but `Transaction` deliberately doesn't carry one — the dataclass shape predates the broker-import stories, and adding a timestamp now without also adding a broker reference would be a half-measure that doesn't actually solve dedupe (timestamps alone are not unique either).

Because there is no correct dedupe key, `create_many(transactions)` on the transactions repository is deliberately **not an upsert**. It is `INSERT INTO transactions ... `, full stop — no `ON CONFLICT` clause, no application-level dedupe step. This is correct behavior given what `Transaction` is, and it is the same "write what you're given, don't silently swallow" posture the rest of `DefaultInfrastructure` takes.

The cost, named explicitly: **a broker re-sync therefore duplicates `Transaction` rows.** Re-running `import_transactions` against the same `start_date` / `end_date` window inserts the same rows again, every time. For `Holding`, the broker re-sync path uses `replace_broker_holdings` (ADR-0022) which atomically deletes + reinserts — no duplicate, by construction. For `Transaction`, the same `replace_` shape would *destroy* legitimate same-day same-amount transactions the user made through other brokers (the "two identical-looking transactions are not the same transaction" case above), so an atomic replace is the wrong primitive.

**Resolution ownership: the Upstox broker-integration feature.** The correct fix is owned by the upcoming Upstox broker-integration feature, not by this ADR. The likely shape — a nullable `transactions.broker_txn_id TEXT` column plus a partial unique index `CREATE UNIQUE INDEX ... ON transactions(portfolio_id, broker_txn_id) WHERE broker_txn_id IS NOT NULL` — added **together with the dataclass field**, in the same follow-up migration and the same PR, so the application code can never get out of sync with the schema it persists. This ADR does **not** pre-build it: building it now would mean inventing a `broker_txn_id` field the four entity dataclasses don't yet carry, which would commit the rest of this codebase to a shape the Upstox feature has not yet finalized. The "not pre-built" stance is the same "don't decide a question a later feature will decide better" posture ADR-0023 itself took for the broker-API choice.

#### Consequences

- `import_transactions` (and any future equivalent) currently inserts duplicate `Transaction` rows on every re-sync over the same window. This is a known limitation, documented here so neither the next reader of this code nor the next developer hitting the bug has to rediscover it from a support ticket.
- The Upstox broker-integration feature's own ADR (when it lands) will be the right place to decide the exact `broker_txn_id` shape, the partial unique index syntax, and the application-level re-sync dedupe rule. Whatever it decides will ship as one migration + one dataclass-field change in one PR, not as a multi-step evolution that leaves intermediate states where the schema and the code disagree.
- This ADR does not block any other work: every other decision in this ADR (domain extraction, typed columns, lazy-CREATE removal, ADR-0019 reaffirmation) is independent of the transactions-dedupe decision and ships without it.

### 5. Reaffirmations and accepted tradeoffs

- **ADR-0019 still holds** — the unified, managed Postgres + Redis + object storage + secret-manager stack is unchanged. The Infrastructure Protocol (the interface every other component talks through) is unchanged. What this ADR changes is *which tables inside that Postgres* have typed columns and a real migration script, and *who owns the dataclass definitions those tables back*. Both are well within the "interface boundary, not a technology choice" latitude ADR-0019 explicitly granted. A real **compliance test** now enforces ADR-0019's invariants — every `Default*` adapter has a `store/retrieve/query` round-trip test against the real Postgres DSN this repo defaults to, and every typed-table component method (`broker_connections`, `broker_transactions`, `broker_holdings`, the four migrated tables from this ADR) is round-tripped through both the legacy JSONB path and the typed-columns path where both apply. The compliance test fails CI if any of those round-trips regress, which is the same posture ADR-0019's "every component talks to System Infrastructure through an interface" rule deserves.
- **Migration tooling stays as this repo's own `run_migration.sh` + `.sql` + `verify_migration.py`.** No alembic (no version-table upgrade/downgrade chain to maintain; no third-party dependency on the migration image; this project's migrations are small enough — fewer than ten — that the cost of a real framework exceeds the cost of the tooling that already works). No ORM (no SQLAlchemy / Django ORM; the `psycopg` cursor + the four typed-column `INSERT`/`SELECT` statements this ADR introduces are explicit and grep-able, which is the same reason every other migration in `scripts/migrate_*.sql` is plain SQL). `scripts/migrate_core_entities.sql` joins `scripts/migrate_us_stocks.sql` and `scripts/migrate_broker_transactions.sql` as the third real migration in this repo, following the same `MIGRATION_NAME` / `DRY_RUN` / `LOG_FILE` / `EXIT_PASS|EXIT_FAIL` conventions `scripts/verify_migration.py` already encodes.
- **Cross-entity writes are non-atomic, by design, and adding a transaction boundary would require its own ADR.** `Infrastructure` (the protocol) exposes no transaction boundary: a `store(users, ...)` followed by a `store(portfolios, ...)` is two separate Postgres round-trips, not one transaction. This matches prior behavior (the existing `onboard_user` already issues multiple non-atomic stores), it is the simplest shape the interface can have (a real transaction boundary would be a `unit_of_work()` context manager on `Infrastructure`, a new Protocol method, and a real decision about how Postgres-only transactions interact with the Redis-backed cache — too many coupled questions for one ADR), and it is **accepted** as the cost of the simple interface. A follow-up ADR is the right place to decide whether to add `Infrastructure.unit_of_work()` (and what shape), what to do about cross-store atomicity (Postgres-only is straightforward; Postgres + Redis + object storage is the hard version), and what happens to the existing JSONB-blob tables that *currently* rely on application-level sequencing. This ADR does not pre-resolve any of those.
- **Repositories deliberately do not use `cache_get`/`cache_set`.** The repository layer is a thin pass-through over `infrastructure.store/retrieve/query` plus dataclass construction; no caching policy lives in it. Caching is a *read-pattern* concern (what's hot, what's stale, what's safe to evict) and the right place to add it is in whichever component actually exhibits the read pattern (e.g. `DefaultUserPortfolio.synchronize_portfolio` is a natural place for a portfolio-cache; a generic repository-level cache would be the wrong layer, because it would have to either invalidate on every write — back to a no-op — or risk serving stale reads the caller's own contract does not promise). This matches ADR-0019's "Redis is cache, not source of truth" rule and the rest of this codebase's "no caching unless a real, named read pattern demands it" discipline.
- **`quantity` / `amount` are annotated `float` today — the float-precision tradeoff is named here.** This ADR does not change those annotations. The DB columns are real `NUMERIC(18, 4)` / `DECIMAL(18, 4)` (matching the existing `broker_transactions` column shape), so precision beyond float is preserved end-to-end at the storage layer. At the Python layer, `float` truncates per IEEE-754 semantics — a `quantity=0.1` round-trips through Postgres as `0.1000` (preserved) but through Python as `0.1` cast to `float`, which is fine for arithmetic but not for exact equality. **A move to `Decimal` everywhere is a follow-up**, scoped to the broker-integration feature (which already moved to `Decimal` per the STORY-7 connector code in `c01_user_portfolio.py`) — this ADR does not pre-empt that decision, because it would force a same-PR change to every component that constructs `Holding` or `Transaction` and that's a larger blast radius than this pass is scoped for. Recorded here so the next reader knows where the precision boundary is and which ADR to update when `Decimal` lands.

#### Consequences

- **ADR-0019 stands, and a compliance test now enforces it.** No technology choice in ADR-0019 changes — Postgres + Redis + object storage + secret-manager are unchanged; the `Infrastructure` Protocol's interface (store/retrieve/query/publish/subscribe/schedule/cache_get/cache_set/get_secret) is unchanged; the only changes are *which tables inside that Postgres* have typed columns and a real migration script, and *where the four core entity dataclasses live*. The compliance test round-trips every typed-table method (the existing `broker_connections`/`broker_transactions`/`broker_holdings` and the four new migrated tables from this ADR) through the live `DefaultInfrastructure` DSN this repo defaults to, and fails CI if any of them regress — which means ADR-0019's "interface boundary, not a technology choice" latitude is now load-bearing rather than aspirational.
- **Migration tooling stays this repo's own.** `run_migration.sh` + `scripts/migrate_core_entities.sql` (this pass's new migration) + `scripts/verify_migration.py` round-trip the four migrated tables; no alembic, no ORM, no second tooling stack. The cost of adopting a real framework would be larger than the cost of the existing tooling for fewer-than-ten migrations, which is the right place to draw the line — recorded here so the question is answered, not deferred.
- **Cross-entity writes remain non-atomic** (`Infrastructure` exposes no `unit_of_work()`), accepted as the cost of the simple interface and matched against prior behavior (`onboard_user` already issued multiple non-atomic stores). Adding a transaction boundary would require its own ADR because it forces decisions on Postgres-only-vs-cross-store atomicity, how the cache participates, and how migration-tooling compatibility is preserved — none of which this ADR has the basis to commit to.
- **Repositories deliberately do not cache.** A repository is a thin pass-through over `Infrastructure.store/retrieve/query` plus dataclass construction, and no caching policy lives there. A future cache for portfolio reads belongs on whichever component exhibits the read pattern (e.g. `DefaultUserPortfolio.synchronize_portfolio`), not at the repository layer, where it would have to either invalidate on every write (back to a no-op) or risk serving stale reads the caller's contract doesn't promise. This matches ADR-0019's "Redis is cache, not source of truth" rule.
- **`quantity` / `amount` stay annotated `float` in this ADR.** The DB columns are real `NUMERIC(18, 4)` / `DECIMAL(18, 4)` so precision beyond float is preserved end-to-end at the storage layer; the truncation only happens at the Python boundary. The move to `Decimal` is owned by the broker-integration feature and recorded explicitly per the story's "note the float-precision tradeoff for quantity/amount if those fields are annotated float" requirement.

## Migration file path and manual rollback SQL

**Migration file path:** `scripts/migrate_core_entities.sql` (run through `scripts/run_migration.sh` with the same `DATABASE_URL` / `MIGRATION_DRY_RUN` / `LOG_FILE` environment variables every other migration in this repo already uses; migration name `core_entities_v1`; one row appended to `migration_log` per invocation, exactly like `us_stock_portfolio_defaults_v1` / `broker_transactions_v1`).

**Manual rollback SQL** (executed by hand, *not* by `verify_migration.py` — the legacy JSONB `data` column is retained, so this is a clean, data-preserving rollback to the pre-ADR-049 state, not a destructive drop):

```sql
BEGIN;

-- 1. Drop the partial unique indices that didn't exist before this ADR.
--    (None on users/portfolios/holdings/transactions in this pass — recorded
--    so a future reader knows the partial-unique-index shape is reserved
--    for the Upstox broker-integration feature, per decision 4 above.)
--    Placeholder, intentionally empty: kept here so the rollback script
--    mirrors the migration script's structure and a future addition has
--    an obvious place to land.
-- DROP INDEX IF EXISTS ... ;

-- 2. Drop the four typed-column tables in FK-safe order:
--    transactions + holdings reference portfolios → drop them first.
DROP TABLE IF EXISTS transactions CASCADE;
DROP TABLE IF EXISTS holdings CASCADE;
DROP TABLE IF EXISTS portfolios CASCADE;
DROP TABLE IF EXISTS users CASCADE;

-- 3. The legacy JSONB payload rows (in the `records` table, with
--    table_name IN ('holdings','portfolios','users','transactions')) are
--    NOT touched by this rollback — they are the source-of-truth recovery
--    point. A `DefaultInfrastructure` reconfigured to dispatch all four
--    tables through the legacy JSONB path (i.e. `MIGRATED_TABLES`
--    emptied for these four entries, then restart) recovers full
--    functionality against the pre-ADR-049 schema.

COMMIT;
```

The legacy JSONB `data` column is retained by the forward migration specifically to make this rollback possible without data loss. Recorded explicitly so no future cleanup pass drops `data` without understanding this ADR's commitment to the rollback path.

## Alternatives considered

- **Leave the four dataclasses in `c01_user_portfolio.py` and just add typed columns + repositories.** Rejected: the circular-import hazard (c01's transitive surface now includes `KnowledgeEntity`, `UpstoxConfig`, `_UpstoxHttp`, `BoundaryGate`, `ExchangeRateFetchError`, etc., every one of which is a real module-load-time dependency a future broker-sync module would have to fight) is a problem this ADR exists to solve. Domain extraction is the right fix; "add repositories without moving the dataclasses" leaves the import-graph hazard in place for the next story that touches it.
- **Have repositories own the SQL directly** (instead of putting `MIGRATED_TABLES` on `DefaultInfrastructure`). Rejected because it splits the SQL for the four core tables across N repository modules and one infrastructure module, which is exactly the duplication `MIGRATED_TABLES` exists to avoid — every repository would re-implement the same column-aware `INSERT` / `SELECT` / `ON CONFLICT` clause set, and any column addition would have to touch all of them in lockstep. ADR-0019's "SQL lives in infrastructure, components see dicts" rule applies here for the same reason it applied for `broker_connections` and `broker_transactions`.
- **Use a real ORM** (SQLAlchemy / Tortoise / Django ORM) for the four migrated tables, even while keeping `psycopg` + raw SQL for everything else. Rejected: introducing a second persistence style in the same `DefaultInfrastructure` doubles the mental model for "how does a row get into Postgres" with no payoff this codebase needs (the four typed tables are four small, fixed tables; the cost of an ORM is amortized over a much larger schema than this project has). The `psycopg` cursor + the registry-dispatched SQL is the right fit.
- **Make `Transaction` carry a `user_id` (or some other natural identity)** as a quick dedupe hack. Rejected: `user_id` is not a transaction-identity field (a single user has many transactions; many users don't share transactions); inventing a "natural identity" out of `(portfolio_id, kind, amount, day)`-ish fields would still fail the "two identical-looking transactions are not the same transaction" case above. The right answer is `broker_txn_id`, owned by the broker-integration feature, not a fake-now-then-redesign-later shape.
- **Drop the legacy JSONB `data` column in the forward migration** rather than retaining it for rollback. Rejected: a destructive forward step with no tested rollback is exactly the kind of "irreversible change made casually" pattern ADR-0019's `verify_migration.py` round-trip discipline exists to prevent. Retaining `data` costs one column of disk per row in exchange for a real, documented rollback path — that is the right trade.
- **Add `unit_of_work()` to the Infrastructure protocol in this ADR** to make cross-entity writes atomic. Rejected: it is the right eventual answer, but it is its own ADR (deciding Postgres-only vs. cross-store atomicity, deciding how the cache participates, deciding migration-tooling compatibility) and bundling it here would force this ADR to commit to answers it doesn't have the basis to commit to. The non-atomicity is accepted as the cost of a simple interface; a follow-up ADR is the right place to revisit it.

## Consequences

- **Broker-sync code can now use repositories without importing `c01`'s component classes**, and the circular-import hazard is gone. `src/upstox_http.py`, `scripts/migrate_broker_transactions.py`, and any future broker-side module can `from domain import Transaction, Holding, USERS_TABLE` without pulling in `KnowledgeEntity`, `UpstoxConfig`, `BoundaryGate`, etc. — and without the deferred-import workaround `DefaultUpstoxBrokerConnector.__init__` already has to use. The existing deferred import can be removed in a follow-up PR; this ADR doesn't remove it (that's a refactor, not a decision change).
- **FKs, list predicates, and broker re-sync idempotency on `holdings` are now real SQL guarantees**, not application-level invariants that have to be re-implemented per caller. The cost is one registry on `DefaultInfrastructure` + one drift-guard test + four real migration columns; the benefit is the same invariants every other typed table in this repo already enjoys.
- **`MigrationRequiredError` replaces the silent-no-op posture** for the four tables that hold the user's portfolio. The other tables (queue tables, `tmp_us_tickers`, `migration_log`, `schema_migrations`, future broker-integration tables) keep the lazy `CREATE TABLE IF NOT EXISTS` mechanism unchanged — this ADR only removes it where a real, named migration script exists.
- **Broker re-sync currently duplicates `Transaction` rows**, by design, with resolution owned by the Upstox broker-integration feature. This is named here so neither the next reader of this code nor the next developer hitting the bug has to rediscover it from a support ticket. The fix will land in one PR (dataclass field + migration + application code) when the Upstox feature finalizes the `broker_txn_id` shape.
- **`created_at` / `updated_at` shipped on all four migrated tables; no FK had to be dropped for legacy or behavioral reasons.** Recorded explicitly per the story's "record whether created_at/updated_at shipped and whether any FK had to be dropped" requirement.
- **Cross-entity writes remain non-atomic**, accepted as the cost of the simple Infrastructure interface, with adding a transaction boundary explicitly identified as needing its own ADR.
- **`quantity` / `amount` stay annotated `float`** in this ADR; precision beyond float is preserved in the DB but truncated in the Python layer; the move to `Decimal` is a follow-up scoped to the broker-integration feature. Recorded explicitly per the story's "note the float-precision tradeoff for quantity/amount if those fields are annotated float" requirement.
- **Repositories stay SQL-free** (zero SQL outside `DefaultInfrastructure`); the column-aware `INSERT` / `SELECT` lives in one place, dispatched from a registry, testable via a single drift-guard test.
- **ADR-0019 is reaffirmed and now enforced by a compliance test** — every typed-table component method round-trips through both the legacy JSONB path and the typed-columns path where both apply, so a regression in either path fails CI before it ships.
- **The migration tooling stack is unchanged** — `run_migration.sh` + `scripts/migrate_core_entities.sql` + (a follow-up) `scripts/verify_core_entities.sql` join the existing `migrate_us_stocks.sql` / `migrate_broker_transactions.sql` as the third real migration in this repo. No alembic, no ORM, no second tooling stack to maintain.
