# 0025 — Tool interchangeability closes CircuitBreaker.find_alternative()'s design gap

**Status:** Accepted — 2026-08-26
**Component:** Tools & Environment (11), Reliability & Resilience (15), Agent Runtime (10)

## Context

ADR-0016 scoped the circuit breaker to per-tool tripping and explicitly named the gap it couldn't close: `CircuitBreaker.find_alternative(tool_name)` — fig 15.1's "alternative exists?" branch — needs a mapping of which tools are interchangeable, and that mapping "depends on Tools & Environment (component 11, not yet designed)." Pending that, `DefaultCircuitBreaker` shipped accepting only an optional caller-supplied `alternatives: dict[str, str]`, honest that it returns `None` with nothing configured.

Separately, `DefaultRecoveryManager.recover()` in Agent Runtime (ADR-0004, revised by ADR-0015) trips the circuit breaker on a `FailureType.LOOP_OR_CASCADE` classification and then always escalates — it never checked `find_alternative()` at all, so fig 15.1's alternative-exists branch was not just unimplemented, it wasn't even reachable from the one place that trips the breaker.

Now that Tools & Environment is designed and implemented (ADR-0024), it can produce that mapping for real: `DefaultToolsEnvironment.alternatives_for(tool_name)`, derived from the same capability-tag rule ADR-0024 already established for `select_tool`/`discover_tool` (two tools are alternatives if they share a tag in `Tool.schema["tags"]`). This ADR is about wiring that real mapping into the two places that were left waiting on it, per `loop.md`'s instruction to update whichever of `DefaultCircuitBreaker` or `DefaultRecoveryManager` the fix actually belongs in — both, as it turns out, once the code was read: the mapping needs to reach `find_alternative()`, and `find_alternative()` needs to actually get called before escalating.

## Decision

**`DefaultToolsEnvironment.alternatives_for(tool_name) -> list[str]`** is the real interchangeability mapping: it looks up the registered `Tool` for `tool_name`, and returns the names of every other registered tool sharing at least one capability tag. Not part of the `ToolsEnvironment` Protocol (that Protocol has no such method) — a real accessor, the same shape as `DefaultTaskManager.status()` in Agent Runtime, callable directly and also handed to `DefaultCircuitBreaker` as documented below.

**`DefaultCircuitBreaker` gains an `alternative_source: Callable[[str], list[str]] | None` constructor parameter**, alongside the existing static `alternatives: dict[str, str]` (kept, checked first, for an explicit caller-pinned override). `find_alternative(tool_name)` now: returns the static-dict entry if one exists; else, if `alternative_source` is configured, calls it and returns the first candidate that `is_available()` still reports up; else returns `None`, unchanged from before this ADR. `DefaultToolsEnvironment.__init__` constructs its own `DefaultCircuitBreaker` with `alternative_source=self.alternatives_for` whenever no circuit breaker is injected — the mapping is wired in by default, not left for every call site to remember to pass.

**`DefaultRecoveryManager.recover()` now completes fig 15.1's branch it previously skipped.** On `FailureType.LOOP_OR_CASCADE`, after tripping the failed tool, it calls `self._circuit_breaker.find_alternative(event.tool)`. If an alternative exists, `recover()` returns a continued `Checkpoint` (same id, `subgoal` merged with `{"preferred_tool": alternative}`) instead of escalating — matching fig 15.1's "alternative exists? -> yes: continue" path. Escalation now only fires when no alternative exists, or the failure has no associated tool at all — the "no" branch of the same diagram, not the unconditional behavior it was before this ADR.

## Alternatives considered

- **Wire the mapping only into `DefaultCircuitBreaker`, leave `DefaultRecoveryManager` unchanged.** This is what "closing the gap" could have meant literally — `find_alternative()` would work correctly if called. Rejected as incomplete: nothing in the codebase calls `find_alternative()` if `DefaultRecoveryManager` doesn't, so `find_alternative()` would be real but dead — callable, tested in isolation, and never reached by the one control-flow path (LOOP_OR_CASCADE handling) fig 15.1 draws it into.
- **Wire the mapping only into `DefaultRecoveryManager`, bypass `find_alternative()` entirely** (e.g., have `DefaultRecoveryManager` call `DefaultToolsEnvironment.alternatives_for` directly). Rejected: it would require `c10_agent_runtime.py` to import from `c11_tools_environment.py`, an Agent-Runtime-depends-on-a-specific-component coupling the existing design avoids (Agent Runtime's Protocols reference Tools & Environment only by interface, e.g. `Executor.act()`'s docstring). Going through `CircuitBreaker.find_alternative()` keeps `DefaultRecoveryManager` depending only on the `CircuitBreaker` Protocol it already depends on; only `DefaultToolsEnvironment`'s own constructor needs to know about both `DefaultCircuitBreaker` and its own `alternatives_for`, which it does either way.
- **Replace the static `alternatives: dict` parameter entirely** rather than keep it alongside `alternative_source`. Rejected: the existing `tests/cross_cutting/test_reliability.py` tests construct `DefaultCircuitBreaker(alternatives={...})` directly, and a caller may legitimately want to pin a specific override without depending on Tools & Environment's tag-derived mapping at all (e.g., a manually-curated emergency substitution). Keeping both, static-dict-first, preserves that use case without regressing existing behavior.

## Consequences

- `find_alternative()`'s behavior now depends on which tools happen to be registered in whatever `DefaultToolsEnvironment` instance constructed the injected circuit breaker, and on those tools' `schema["tags"]` being populated meaningfully (ADR-0024) — a circuit breaker built standalone (`DefaultCircuitBreaker()` with no arguments, as `DefaultRecoveryManager`'s own default still does) has no `alternative_source` and behaves exactly as before this ADR: `find_alternative()` returns `None` unless a static `alternatives` dict was passed. Nothing breaks for existing callers that don't opt in.
- `DefaultRecoveryManager.recover()`'s return value on `LOOP_OR_CASCADE` is no longer only "raise `EscalationRequired`" — it can now return a `Checkpoint` on that path too, same as the `TRANSIENT` path. Callers that assumed `LOOP_OR_CASCADE` always escalates (there were none in this codebase before this ADR; `test_agent_runtime.py`'s existing loop/cascade test uses a fresh `DefaultCircuitBreaker()` with no alternative configured, so it still escalates and still passes) must not assume that going forward.
- `preferred_tool` on a replanned `Checkpoint.subgoal` is a real signal with no real consumer yet: `placeholder_reason_fn` (ADR-0021) does not look at `subgoal` at all, so this continuation is bookkeeping-correct but has no effect on which tool actually gets called next until a real `reason_fn` exists and chooses to honor it. That is the same honest scope `DefaultRecoveryManager`'s own docstring already claims for replanning generally — this ADR does not change that.
- `switch_tool` (component 11's own operation) and `find_alternative` (component 15's) now use the same underlying `alternatives_for` data through two different call paths — a tool can be swapped explicitly via `DefaultToolsEnvironment.switch_tool()` or implicitly via a tripped circuit breaker's `find_alternative()`. Both respect `is_available()`, so a tool that is itself tripped is never returned as someone else's alternative.
