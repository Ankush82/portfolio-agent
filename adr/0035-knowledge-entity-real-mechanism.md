# 0035 — Knowledge & Entity Model real mechanism: normalized exact match + edit-distance fuzzy fallback, Infrastructure-backed CRUD, documented merge transfer rule

**Status:** Accepted — 2026-08-26
**Component:** Knowledge & Entity Model (04)

## Context

`src/components/c04_knowledge_entity.py` was whiteboard-only before this pass — `KnowledgeEntity(Protocol)` and `StubKnowledgeEntity` only, no low-level design, no ADR. Component 05 already calls this component for real (`DefaultRetriever.resolve_entity`, ADR-0033) and has been doing so against `StubKnowledgeEntity` (always `None`) since that round landed, so this component's real behavior has been a live gap, not a speculative one.

Read Data Processing & Quality (03) first, as instructed, to check the actual shape of what feeds this component: `StructuredData(source_id, fields: dict)` (ADR-0032), where `fields` may carry real extracted content (JSON keys pass through directly; text yields `dates`/`numbers`/`labeled_fields`, and after `transform()`, flattened dot-notation keys) alongside reserved metadata keys — `"provenance"` (ADR-0003 tag, always `"UNTRUSTED"` for anything that passed through `extract()`), `"_fetched_at"`, `"_duplicate_of"`, `"_content_hash"`. Nothing in that shape hands this component a ready-made `Entity`; a caller (an ingestion pipeline not yet built) is expected to read fields like `labeled_fields.Ticker` out of a `StructuredData` and construct a `details` dict for `create_entity` itself. This component's `create_entity(details: dict)` signature already anticipates exactly that — a free-form dict, not a typed `StructuredData` parameter.

Per this round's operating-mode instruction, the design gaps below are resolved here with documented engineering judgment (Status: Accepted, not Proposed) rather than left open — entity resolution/canonicalization is a real structural/lookup problem against a known registry, not a task needing generation, so none of it hits the genuine external-credential exception ADR-0021's template exists for.

## Decision

**Registry: two `Infrastructure`-backed tables**, never an in-memory dict (ADR-0019's boundary honored throughout, `DefaultInfrastructure` by default):

- `"entities"` — one row per entity: `{"id", "kind", "name", "aliases": [str, ...], "attributes": dict, "provenance"?, "merged_into"?}`. A row carrying `"merged_into"` is a tombstone left behind by `merge_entities` (see below).
- `"relationships"` — one row per link: `{"id", "source_entity_id", "target_entity_id", "kind"}`. `id` is this component's own synthesized row key (the `Relationship` dataclass itself carries no id), which is what lets `merge_entities` repoint a specific row's source/target in place.

**`resolve_entity(mention)`: normalized exact match, then a real fuzzy fallback, never only exact.** The mention is normalized (lowercased, whitespace-collapsed) and checked against every live entity's normalized name + aliases for an exact match first. If none clears, every live entity's names/aliases are scored against the mention with normalized Levenshtein edit-distance similarity (`1 - distance / longer_length`); the highest-scoring entity is returned if its score meets `_DEFAULT_FUZZY_MATCH_THRESHOLD = 0.80` (constructor-overridable), else `None` — an honest "nothing cleared the bar," not a forced guess.

**Edit distance, not Jaccard token overlap, for this matching shape.** The project already has a token-overlap precedent (`DefaultEntityLinker` in c06_memory.py, `DefaultEvidenceLinker` in c09, both ADR-0006/ADR-0029) for relatedness between *content* (multi-sentence memories, claims). Entity mentions are a different shape: short strings (company/security/person names), where the dominant real-world noise is a handful of character-level edits — a typo, a missing "Inc.", a punctuation slip — not vocabulary substitution. Token overlap is blind to that: a single-character typo turns a name into a token that shares zero tokens with the original ("Aple" vs. "Apple" — Jaccard 0.0), which is exactly the case fuzzy matching exists to catch. Edit distance measures character-level closeness directly, which is the actual failure mode here.

**Threshold: 0.80.** Chosen so a name with one or two character edits on a medium-length string still matches (`"Aple Inc"` vs. `"Apple Inc"`: edit distance 1, longer length 9, similarity ≈0.89) while short, genuinely different strings still don't (`"AB"` vs. `"AC"`: distance 1, longer length 2, similarity 0.50) — a real, non-arbitrary property of ratio'd edit distance on short strings: it demands near-exact matches for short names and tolerates proportionally more edits for longer ones, which matches how much a couple of characters actually change the identity of a two-letter ticker versus a full company name.

**`create_entity`/`update_knowledge`: real CRUD, "kind" and "name" required.** `create_entity` raises `ValueError` if `details` lacks a non-empty `"kind"` or `"name"` — `Entity.kind` is a required dataclass field, and an entity with no name could never be resolved by mention again, defeating this component's purpose. Every other key in `details` (beyond the reserved `id`/`kind`/`name`/`aliases`/`provenance`) is stored under `"attributes"`. `update_knowledge(entity, updates)` writes `"kind"`/`"name"`/`"aliases"` directly (replace, not merge — a caller wanting to extend aliases passes the full desired list) and everything else into `"attributes"`; if `entity`'s record has been merged away, the update redirects onto the surviving entity (see below) rather than silently landing on a tombstone no one can look up again.

**`merge_entities(a, b)`: `a` is the documented survivor, `b` the loser — real alias/relationship transfer, not a silent drop.**
- The loser's canonical name becomes an alias of the survivor, and the loser's own aliases are appended (deduplicated by normalized form, survivor's existing aliases kept first) — so any mention that used to resolve to `b` still resolves, now to `a`.
- The loser's `attributes` fill in any keys the survivor doesn't already have; the survivor's own values win on conflicts (survivor is the trusted record going forward).
- Every `"relationships"` row referencing the loser's id (as source or target) is rewritten in place to reference the survivor instead — a real repoint through the same `Infrastructure` interface, not left dangling and not duplicated.
- The loser is left behind as a tombstone (`{"id": b.id, ..., "merged_into": a.id}`) rather than deleted — `Infrastructure` (ADR-0019) has no delete primitive, and the tombstone is exactly what lets `update_knowledge` redirect a stale reference onto the survivor instead of silently no-oping.

**`link_entities`/`represent_relationships`/`query_relationships`: real relationship storage and lookup.** `link_entities` stores one row per call; `represent_relationships`/`query_relationships` query `"relationships"` twice per call (once as `source_entity_id`, once as `target_entity_id` — `Infrastructure.query`'s containment filter is single-condition AND, no OR support, so a real "either side" lookup needs two queries merged and deduplicated by row id) and reconstruct `Relationship` objects from the stored rows. `query_relationships(entity, kind=...)` adds `kind` to both filters for a real, not simulated, kind-scoped result.

**Provenance: propagated forward when supplied, never fabricated, never re-tagged.** This component canonicalizes already-processed `StructuredData` — it does not ingest raw external content itself, so `DefaultBoundaryGate.tag_provenance` (ADR-0003) is not called anywhere in this class; that boundary crossing already happened in Data Processing & Quality (03). `create_entity` does propagate a `details["provenance"]` key through onto the stored entity record when a caller supplies one (e.g., copied from `StructuredData.fields["provenance"]` by an upstream ingestion caller), so the untrusted-content signal isn't lost at this hop — but nothing here invents a provenance value when the caller doesn't provide one.

## Alternatives considered

- **Jaccard token overlap for `resolve_entity`'s fuzzy fallback**, matching the project's existing precedent exactly (c06/c09). Rejected for the reason above: entity mentions are short, and token overlap's failure mode (a single typo produces a token with zero overlap with the original) is precisely the case fuzzy matching needs to cover for names, not content.
- **Deleting the loser outright in `merge_entities`.** Simpler, and arguably more honest about "this entity no longer exists" — but `Infrastructure` has no delete primitive (ADR-0019's interface is store/retrieve/query/publish/subscribe/schedule/cache/secret, nothing else), and a hard delete would leave any relationship row or external reference still carrying the loser's id pointing at nothing retrievable. Rejected in favor of a tombstone plus `update_knowledge`'s redirect, which keeps the system honest about "this id still means something, just not independently anymore."
- **Merging attributes with the loser's values winning conflicts.** Rejected — the survivor is the entity callers chose to keep as canonical; letting the loser silently overwrite the survivor's own recorded attributes would make `merge_entities(a, b)` behave differently depending on which entity happened to be `b`, which is a worse property for a documented, deterministic rule to have.
- **Extending `resolve_entity`'s signature to accept a `kind` hint**, so fuzzy matching could disambiguate a `Person` named similarly to a `Company`. Rejected: the `KnowledgeEntity` Protocol's signature (`resolve_entity(self, mention: str) -> Entity | None`) is fixed by the whiteboard design this round was handed, and no ADR authorizes changing it. Named here as a real, stated scope limit rather than silently worked around.

## Consequences

- Fuzzy matching is real and deterministic but purely lexical — two differently-punctuated or slightly-misspelled forms of the same name will match; two short, unrelated names sharing most of their characters by coincidence (rare, but possible for tickers) could false-positive. No `kind` disambiguation exists to reduce this (see Alternatives above) — a real, named limitation, not a silent one.
- `resolve_entity` and the merge-time alias/relationship transfer both do full, unindexed scans over the `"entities"`/`"relationships"` tables via `query(table, {})`/single-field containment queries — real correctness today, not real scale; acceptable for this pass given no dedicated search/index infrastructure exists anywhere in this project yet, and revisit if the entity registry grows large enough for this to matter.
- A caller holding a pre-merge `Entity` reference to the loser still gets correct behavior from `update_knowledge` (redirected to the survivor) and from `represent_relationships`/`query_relationships` called with the *survivor's* id (relationships were physically repointed) — but calling `represent_relationships`/`query_relationships` with the stale loser `Entity` directly returns nothing, since those two methods query relationships by id directly and don't consult the tombstone's `merged_into` redirect the way `update_knowledge` does. Named here as a real, asymmetric scope limit: only `update_knowledge` currently redirects a stale reference, not every method that takes an `Entity`.
- This component still does no semantic/NER-style entity extraction from prose — that gap is the same LLM-provider boundary ADR-0021/ADR-0032 already named; `resolve_entity` only ever matches a mention string a caller already extracted (structurally, e.g. component 05's capitalized-word heuristic) against a known registry, it doesn't discover new entity mentions in raw text itself.
