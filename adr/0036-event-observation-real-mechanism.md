# 0036 — Event & Observation real mechanism: percent-change floor, z-score anomaly rule, rule-based event aggregation/classification, real entity linking, time-windowed correlation

**Status:** Accepted — 2026-08-26
**Component:** Event & Observation (07)

## Context

`src/components/c07_event_observation.py` was whiteboard-only before this pass — `EventObservation(Protocol)` and `StubEventObservation` only, no low-level design, no ADR. The four dataclasses it exposed (`Observation(entity_id, metric, value)`, `Change(observation, delta)`, `Anomaly(observation, reason)`, `Event(id, type, entity_ids)`) were read first, as instructed, rather than assumed — none of them carried a timestamp, an identity for `Observation`, a computed `percent_change` for `Change`, a computed `magnitude` for `Anomaly`, or an originating `metric`/`magnitude`/`detected_at` for `Event`. A real (not stubbed) implementation of every capability this round's task named — `observe`, `detect_change`, `detect_anomaly`, `detect_event`, `classify_event`, `link_event_to_entities`, `correlate_events`, `retrieve_events` — genuinely needs all of that: `detect_change`/`detect_anomaly` need to find "the prior observation for this entity/metric" against real stored history, which needs an identity and a real ordering signal; `detect_event` needs a real timestamp to persist and for `correlate_events` to use; `classify_event` needs to know what metric an event actually originated from to classify it by anything other than a name it doesn't have.

Read Knowledge & Entity Model (04) first, as instructed, to check `DefaultKnowledgeEntity`'s real shape (ADR-0035): `resolve_entity(mention) -> Entity | None` (normalized exact match, then edit-distance fuzzy fallback), `link_entities(a, b, relationship) -> Relationship`, `query_relationships(entity, kind=None) -> list[Relationship]`. Nothing in that shape expects an already-canonical entity id — `resolve_entity`'s own signature calls its input a "mention," and 04's docstring is explicit that entity resolution is "a real structural/lookup problem against a known registry," which is exactly the job `link_event_to_entities` needs to hand off rather than reinvent.

Per this round's operating-mode instruction, the design gaps below are resolved here with documented engineering judgment (Status: Accepted, not Proposed) rather than left open — change/anomaly/event detection over numeric observations is a real statistical and rule-based problem, not a task needing generation, so none of it hits the genuine external-credential exception ADR-0021's template exists for.

## Decision

**Dataclass extensions, the same kind ADR-0032 already made to `RawDocument` (adding `fetched_at`) for the same reason.** `Observation` gains `observed_at: str = ""` and `id: str = ""`; `Change` gains `percent_change: float = 0.0`; `Anomaly` gains `magnitude: float = 0.0`; `Event` gains `metric: str = ""`, `magnitude: float = 0.0`, `detected_at: str = ""`. All additive with defaults — no existing call site (there are none yet; this component had no real caller before this pass) breaks. Every field is either genuinely load-bearing for a real implementation (`Observation.id`/`observed_at` for history ordering, `Event.metric` for classification, `Event.detected_at` for correlation) or a computed diagnostic a real caller would want (`Change.percent_change`, `Anomaly.magnitude`).

**Registry: two `Infrastructure`-backed tables**, never an in-memory dict (ADR-0019's boundary honored throughout, `DefaultInfrastructure` by default):

- `"observations"` — one row per recorded observation: `{"id", "entity_id", "metric", "value", "observed_at", "sequence"}`. `"sequence"` is a real, monotonically increasing per-`(entity_id, metric)` counter (the count of prior rows for that pair at insertion time, the same brute-force-but-real counting pattern ADR-0035 already used for its own unindexed scans) — the ordering signal `detect_change`/`detect_anomaly`'s history lookups actually rely on, since a caller-supplied `observed_at` string alone gives no guaranteed tie-break between two observations recorded in the same second.
- `"events"` — one row per detected event: `{"id", "type", "entity_ids", "metric", "magnitude", "detected_at"}`, written by `detect_event` and read back by `retrieve_events`.

**`observe(raw)`: real validation plus a real stored record.** Raises `ValueError` on a missing/empty `entity_id`, `metric`, or `value` — an observation with no metric or entity can never be looked up again, the same "can never be resolved again" reasoning ADR-0035 used for `create_entity`'s required `name`. `observed_at` defaults to now (`%Y-%m-%dT%H:%M:%S`, matching c02/c03's existing timestamp format) when the caller doesn't supply one.

**`detect_change(current, prior)`: a real percent-change floor, `0.02` (2%).** Both observations are supplied by the caller (the Protocol's own fixed signature, unchanged here — no ADR authorizes changing it, same posture ADR-0035 took toward `resolve_entity`'s signature). 2% is small enough to catch a genuine intraday move in a financial metric (price, volume, a fundamentals figure) while filtering out sub-percent jitter indistinguishable from measurement/rounding noise for this domain — overridable per instance via the constructor, a documented default, not a silent magic number. When `prior.value == 0`, percent change is undefined by division; a nonzero delta off a zero baseline is treated as automatically clearing the floor (a real move from nothing is never noise), a delta of exactly zero still yields "no real change."

Where does `detect_change` get a real `prior`, given its own signature takes one as a parameter rather than looking it up itself? That's `detect_event`'s job (below) — it queries `"observations"` for the immediately-preceding stored record for the same entity/metric (via a private `_prior_observation` helper, matching by `Observation.id` against the `"sequence"`-ordered history) and passes the result into `detect_change` itself. `detect_change`'s own implementation stays a pure, real comparison of two given observations; the real Infrastructure lookup that supplies its `prior` argument lives one level up, in the one caller that actually needs to manufacture it.

**`detect_anomaly(observation)`: a real z-score outlier check against the last N=20 observations, minimum 5, threshold 2.5.** `observation`'s own signature carries no history parameter, so this method queries `"observations"` directly (`_recent_history_values`, excluding `observation` itself by id) — real per-call Infrastructure access, not a hardcoded constant. N=20 balances a stable mean/stdev estimate against staying responsive to a metric whose regime shifts over time; fewer than 5 prior points is reported as "not enough history to judge" (`None`), an honest "unknown," not a guess built on a near-empty sample. Threshold 2.5 is roughly the 98.8th percentile two-tailed under a normal approximation — deliberately stricter than `detect_change`'s 2% floor, since "anomalous" is meant to be a rarer, stronger claim than "changed." Sample standard deviation (`statistics.stdev`, Bessel's correction) is used rather than population stdev, treating recent history as a sample of a larger process rather than the entire population — the standard choice for this shape of check. When the history has zero variance (a genuinely constant series), a z-score is undefined by division; a differing current value is still reported anomalous (deviation from a constant is real evidence), using absolute deviation from the mean as the documented magnitude proxy in that one case.

**Every real anomaly is recorded via `AuditManager` (`DefaultAuditManager` by default); changes are not.** An anomaly is exactly the kind of surprising, worth-a-record signal `AuditManager.record`'s own docstring already names quarantine decisions (Memory, ADR-0007) and blocked claims (Evidence & Verification, ADR-0013) as — the same category of event. A change that only clears the 2% floor is common, expected traffic; auditing every one would flood the log with routine data rather than surface the surprising cases an audit trail exists for.

**`detect_event(observations)`: real rule-based aggregation — an anomaly always qualifies, a change only qualifies above a stricter 5% magnitude bar.** For each given observation: `detect_anomaly` runs first (its own result already cleared a much stronger statistical bar, so it always qualifies as an event trigger); otherwise, the immediately-preceding observation is looked up and `detect_change` is run, qualifying only if `abs(percent_change) >= 0.05` — a documented, stricter floor than `detect_change`'s own 2%, because not every real change is worth surfacing as an Event for downstream components to act on. Every triggering observation's `entity_id` contributes to `entity_ids` (deduplicated, order preserved); the single strongest-magnitude trigger across the batch decides the event's `metric`/`magnitude`, which `classify_event`'s rule (below) turns into `type`. Returns `None` when nothing in the batch clears the bar. The resulting `Event` is persisted to `"events"` before being returned, so `retrieve_events` can find it later.

**`classify_event(event)`: real, metric-name keyword rule — category is what's measured, not how much it moved.** `"earnings"` for metric names containing `earnings`/`eps`/`revenue`/`profit`/`net_income`/`guidance`; `"market_movement"` for `price`/`close`/`open`/`volume`/`market_cap`/`shares`; `"general"` otherwise — case-insensitive substring match, so `"quarterly_revenue"` still matches `"revenue"`. Deliberately not a function of `event.magnitude`: a 3% EPS move and a 30% EPS move are both "earnings" events, so magnitude isn't a classification axis — it's still carried on `Event` for any downstream consumer (e.g. Decision & Policy) that wants severity as an independent signal, just not folded into `type` here. `detect_event` calls the same underlying rule (a shared private `_classify` helper) to populate `Event.type` at construction time, so `classify_event` itself is a pure re-application of the identical rule, not a second, possibly-diverging classifier.

**`link_event_to_entities(event)`: real resolution and linking, delegated to `KnowledgeEntity`, not reinvented.** `Observation.entity_id` (and therefore `Event.entity_ids`) is treated as a *mention* — whatever identifier string the raw observation feed uses (a ticker, a company name) — not assumed to already be a canonical `Entity.id`. Every mention is resolved via `self._knowledge_entity.resolve_entity(mention)` (`DefaultKnowledgeEntity` by default, injectable); unresolvable mentions are dropped, never fabricated into a new entity — this component doesn't own entity-creation policy, only linking and detection. Every resolved pair is linked via `self._knowledge_entity.link_entities(a, b, "co_occurred_in_event")` — a real knowledge-graph edge recording that these entities co-occurred in a detected event, not just a returned list of ids. Returns the resolved entities' canonical ids.

**`correlate_events(events)`: real pairwise rule — shared or knowledge-graph-related entities, within a one-hour window.** Every pair in the given list is checked: they correlate only if `detected_at` on both sides is parseable and within `_correlation_time_window_seconds` (default 3600 — one hour) of each other, **and** either they directly share an `entity_id`, or their entities are linked in the knowledge graph (`KnowledgeEntity.query_relationships`, e.g. two companies in the same sector). One hour is chosen because financial events for the same or related entities landing within the same trading-session window plausibly describe the same real-world development (an earnings anomaly and a market-movement event for the same company minutes apart); events days apart that happen to share an entity are a coincidence of scope, not a real temporal correlation. A missing or unparseable `detected_at` on either side conservatively excludes the pair — can't confirm proximity, won't guess — the same posture `detect_stale_data` (ADR-0032) already took toward unparseable timestamps.

**`retrieve_events(filters)`: real `Infrastructure`-backed query with real filter support.** `"type"` is pushed down to `Infrastructure.query`'s own containment filter (exact match); `"entity_id"` is a membership test against each event's `entity_ids` list, applied after the query since JSONB containment matching can't test list membership directly; `"since"`/`"until"` are ISO-format timestamp bounds on `detected_at`, inclusive, applied the same way. Unrecognized filter keys are ignored rather than raising, matching `Infrastructure.query`'s own permissive filter-dict contract.

## Alternatives considered

- **Folding `event.magnitude` into `classify_event`'s rule** (e.g. a severity-scaled category, or an `"anomaly"` category distinct from `"earnings"`/`"market_movement"` for anomaly-triggered events specifically). Rejected: category should answer "what kind of thing happened" (a property of the metric), not "how surprising was it" (a property of the trigger mechanism and its magnitude) — conflating the two would make the same metric produce a different category depending on whether it triggered via `detect_change` or `detect_anomaly`, which is a worse property for a documented, deterministic rule to have than keeping `magnitude` as a separate, always-available field.
- **A single shared "real change" threshold for both `detect_change` and `detect_event`.** Rejected in favor of two tiers (2% / 5%): a change clearing only the lower "is this real, not noise" floor is common, expected traffic that's still worth recording as a `Change` for a caller who wants every real move; only a stronger move is worth escalating all the way to an `Event` for downstream components (Memory, Decision & Policy) to act on. Collapsing the two into one number would either flood `detect_event` with routine 2%-3% moves or silence `detect_change` on real-but-modest moves a caller might still want.
- **Auto-creating a new entity in `link_event_to_entities` when a mention doesn't resolve**, rather than dropping it. Rejected — entity-creation policy (what counts as a valid new `Entity`, what `kind` to assign it, whether a low-confidence mention should ever become a permanent registry entry) belongs to whatever component or process owns ingestion into the Knowledge & Entity Model, not to this component's linking step; fabricating entities here would also make `link_event_to_entities` non-idempotent in a way that's hard to reason about across repeated calls on the same event.
- **Correlating events purely by shared entity, no time window.** Rejected — two events for the same company months apart are unrelated developments, not a correlation; the time window is what turns "these mention the same ticker" into "these plausibly describe the same real-world development."
- **Population standard deviation (`statistics.pstdev`) for `detect_anomaly`.** Rejected in favor of sample stdev (`statistics.stdev`, Bessel's correction) — the last N observations are a sample of an ongoing process, not the entire population of all observations that will ever exist for that entity/metric; sample stdev is the standard, slightly more conservative choice for exactly this shape of "is this new point unusual" check.

## Consequences

- `detect_change`'s own implementation never queries `Infrastructure` — its real history lookup lives in `detect_event`'s `_prior_observation` helper instead. A caller invoking `detect_change` directly with two hand-built `Observation`s (as several of this round's own tests do) gets a fully real computation with no Infrastructure dependency at all; a caller wanting "the real prior for this entity/metric" needs to go through `detect_event`, or call the same private lookup pattern itself. Named here as a real, deliberate split rather than a gap — the Protocol's fixed signature makes it the only place a real prior lookup can live without an unauthorized interface change.
- `_prior_observation`'s "observation not found in its own history" fallback (returning the most recently stored record when `observation.id` doesn't match anything, e.g. for a hand-built `Observation` never passed through `observe()`) is a best-effort default, documented in the method's own docstring, not a guarantee — a caller relying on `detect_event` for observations that never went through `observe()` should not expect exact prior-observation semantics.
- `_history_records`/`_recent_history_values`/`_entities_related` all do full, unindexed scans over their respective tables via `Infrastructure.query`, the same "real correctness today, not real scale" tradeoff ADR-0035 already named for its own registry scans — acceptable for this pass given no dedicated search/index infrastructure exists anywhere in this project yet.
- This component still has no real ingestion path from raw external feeds into `observe(raw: dict)` — `raw` is whatever shape a caller hands it (`entity_id`/`metric`/`value`/optional `observed_at`), the same "caller assembles the dict" pattern ADR-0035 already noted for `create_entity(details: dict)`. No genuine external-credential gap exists here either way: this component consumes already-observed numeric data, it doesn't fetch anything itself.
