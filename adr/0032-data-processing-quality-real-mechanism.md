# 0032 — Data Processing & Quality: real mechanism (structural parse/extract, rule-based normalize/transform/dedup/validate, computed quality score, real staleness check, Infrastructure-backed lineage)

**Status:** Accepted — 2026-08-26
**Component:** Data Processing & Quality (03)

## Context

Data Processing & Quality was whiteboard-only before this pass: `src/components/c03_data_processing_quality.py` held a `DataProcessingQuality` Protocol, its dataclasses (`RawDocument`, `ParsedDocument`, `StructuredData`, `DataQualityScore`, `DataLineage`), and a `StubDataProcessingQuality` traced no-op — no mechanism design, no ADRs. This project's operating mode for this pass is to build end to end using engineering judgment rather than pausing for design-tradeoff questions, and to document each real call as an Accepted ADR, not a Proposed draft — that is what this ADR is.

This component's assignment required reading Data & Sources (02) first, since `DefaultDataSources` (ADR-0026) is what actually produces the documents this component consumes. That check surfaced a real gap: `SourceDocument` (component 02's output) carries `source_id`, `content`, and `fetched_at`; `RawDocument` (this component's declared input) only carried `source_id` and `content`. `fetched_at` is not optional bookkeeping here — `detect_stale_data`, one of this component's nine required capabilities, cannot compute a genuine freshness signal without knowing when a document was fetched. This is not an external-credential gap (ADR-0021's shape); it's a whiteboard dataclass that was drawn before anyone checked it against what actually flows into it. Per this pass's operating mode, that's a real decision to make and document, not a reason to stop.

Several other real forks came up making every capability genuinely real rather than a stub:

1. **What "extract" means.** The task named this explicitly: structural field extraction (real, no LLM) versus semantic/entity extraction from unstructured prose (needs real language understanding — the same gap ADR-0021 already named for Agent Runtime's reasoning). Which one to implement, and how to be honest about the other, needed a decision.
2. **How provenance tagging travels forward.** ADR-0003 requires untrusted content to be tagged before it's reasoned over elsewhere; this component produces two new artifacts (`ParsedDocument.structure`, `StructuredData.fields`) that need to carry that tag onward to Evidence & Verification (09), not just note that tagging happened.
3. **How lineage gets tracked for real.** `track_data_lineage` needs `DefaultInfrastructure`-backed persistence (table `"data_lineage"`, per the task) of which pipeline steps actually ran, in order — which means every other method needs to write to that record as it runs, not just this one method fabricating a plausible-looking answer.
4. **How score_data_quality gets a real reliability signal.** The task named "source reliability if available from Source/SourceMetadata" — this component doesn't own that data; component 02 does, and does compute and persist it for real (ADR-0026's `track_source_reliability_metadata`).

## Decision

**1. `RawDocument` gains a `fetched_at: str = ""` field.** Additive, defaulted, so it can't break any other call site (none existed — checked via grep before adding). This is what lets `detect_stale_data` compute a real age rather than a placeholder.

**2. `extract` implements structural extraction only, for real, today.** Already-labeled JSON keys pass through directly (`ParsedDocument.structure["format"] == "json"` → `StructuredData.fields = dict(data)`); free text is mined via regex for ISO-8601 dates, currency/number tokens (date substrings stripped first so a date's year/month/day don't double-count as loose numbers), and already-labeled `"Key: Value"` lines. No entity/semantic extraction is attempted, and `extract`'s docstring says so explicitly rather than silently doing something shallower and calling it done. Deeper extraction is named as depending on ADR-0021's resolution, not given its own duplicate draft ADR — same root cause, one open item.

**3. `DefaultBoundaryGate.tag_provenance` is called inside `parse` and `extract`, not left as a separate step a caller might forget.** `parse` tags the parsed `structure` dict; `extract` tags the extracted `fields` dict. Both merge in a `"provenance"` key (always `"UNTRUSTED"`, per ADR-0003/`DefaultBoundaryGate`'s existing behavior) that travels forward inside `StructuredData.fields` through every subsequent step — `validate` and `score_data_quality` both check for this tag being present and correct as part of their real logic, so a `StructuredData` that skipped `extract`'s tagging is genuinely treated as lower-quality/invalid, not silently accepted.

**4. A reserved-field-key convention (`_RESERVED_FIELD_KEYS`) keeps pipeline metadata separate from real content.** `"provenance"`, `"_fetched_at"`, `"_duplicate_of"`, `"_content_hash"` are metadata keys that ride alongside real extracted content inside the same `fields` dict (StructuredData has one dict, not a metadata/content split) but are excluded from normalize's value-coercion, transform's flattening, and score_data_quality's completeness calculation — so a document's actual content quality is measured on its actual content, not diluted by bookkeeping fields.

**5. `deduplicate` does exact-duplicate detection via a real SHA-256 content hash**, checked against a persisted `"data_processing_dedup"` table (one row per `document_id`, its content hash) — not near-duplicate similarity scoring. See Alternatives for why.

**6. `score_data_quality` is a real weighted sum of three independently computed signals**, each genuinely in [0, 1]: completeness (fraction of non-metadata fields that are actually populated), structural validity (the same rules `validate()` applies, factored into a shared `_is_valid` function so scoring doesn't silently double-log an extra `"validate"` lineage entry nobody asked for), and source reliability — read from component 02's own persisted `"sources"` table (`metadata::{source_id}` row, written by `DefaultDataSources.track_source_reliability_metadata`) when available, else a neutral `0.5`. Weights: completeness 0.4, validity 0.3, reliability 0.3 — completeness and validity weighted slightly higher because they're this component's own, fully-observable signals; reliability is included but weighted lower because it's frequently unavailable today (ADR-0027 is still Proposed, so most sources score `_RELIABILITY_SYNTHETIC_DOCUMENT` or have no row at all).

**7. `detect_stale_data` checks real elapsed time against a documented 24-hour default threshold**, configurable per instance via the constructor. A missing or unparseable `_fetched_at` is treated as stale, not fresh — the conservative default for financial/portfolio data, where "we don't know how old this is" should never read as "this is fine."

**8. `track_data_lineage` is `DefaultInfrastructure`-backed against table `"data_lineage"`, one row per `document_id`, an ordered list of `{"step", "at"}` entries** — not an in-memory dict. Every other real method (`parse`, `extract`, `normalize`, `transform`, `deduplicate`, `validate`, `score_data_quality`, `detect_stale_data`) appends its own name to this record as it completes, via a shared `_record_lineage_step` helper; `track_data_lineage` itself is a pure read and does not append itself — it observes the pipeline, it isn't one of its transforming steps.

## Alternatives considered

- **Leave `RawDocument` without `fetched_at` and derive staleness some other way** (e.g., a separate lookup back into component 02's storage). Rejected: this component's own `Infrastructure` access has no guaranteed way to know which `source_id` maps to which fetch without either duplicating component 02's table-reading logic more invasively than the one read `score_data_quality` already does for reliability, or accepting an untimed document as an unresolvable case. Carrying `fetched_at` forward on the dataclass that's already handed to this component is the minimal, most honest fix, and it's what `SourceDocument` already provides — this component was just dropping it.
- **Attempt LLM-based semantic extraction now, treating it as in scope.** Rejected: this project has never chosen an LLM provider anywhere (ADR-0021's exact finding), and inventing a provider choice here to make `extract` "more complete" would be deciding a real architectural fork by fiat, which this pass's operating mode explicitly reserves for genuine external-credential gaps.
- **Near-duplicate/similarity-based deduplication** (e.g., Jaccard token overlap on content, as `DefaultEntityLinker` already does for Memory in component 06). More powerful — catches reworded duplicates, not just byte-identical ones — but needs a similarity threshold decision with no obvious "correct" value, and a full corpus scan (or an index) to compare against efficiently, versus exact hashing's O(1) lookup by hash value. Exact-hash dedup is the honest, real, defensible mechanism for this pass; near-duplicate detection is a real future enhancement, not pretended away.
- **A metadata/content split on `StructuredData`** (e.g., `StructuredData(source_id, fields, metadata)` instead of one `fields` dict carrying both). Would avoid needing `_RESERVED_FIELD_KEYS` filtering throughout. Rejected: `StructuredData`'s shape is a fixed whiteboard dataclass (`source_id: str, fields: dict`) that the task did not ask to be restructured, unlike `RawDocument`'s genuine missing-field gap; a reserved-key convention achieves the same separation without changing the Protocol's declared shape.
- **`score_data_quality` weights chosen some other way** (e.g., equal thirds, or reliability weighted highest). Equal thirds was considered and rejected because it would let an entirely-unavailable reliability signal (neutral 0.5, the common case today) exert as much influence as this component's own fully-observed signals; the 0.4/0.3/0.3 split keeps reliability's real but currently sparse contribution real without letting its absence flatten every score toward 0.5.

## Consequences

- `parse`, `extract`, `normalize`, `transform`, `deduplicate`, `validate`, `score_data_quality`, `detect_stale_data`, and `track_data_lineage` are all real today — no hardcoded return, no in-memory dict standing in for `Infrastructure`.
- Anything that depends on `extract` performing genuine entity/semantic understanding of prose (as opposed to structural, already-labeled-field extraction) is not yet safe to build on top of this implementation — that gap is ADR-0021's, not a new one.
- `score_data_quality`'s reliability component is silently neutral (`0.5`) for any `source_id` component 02 hasn't ingested yet, or has only ingested via `PlaceholderSourceFetcher` (ADR-0027) — an honest reflection of that ADR still being open, not a bug here.
- `deduplicate`'s exact-hash approach means a reworded near-duplicate is not caught; only byte-for-byte-identical (post-metadata-strip) content is flagged via `_duplicate_of`.
- `RawDocument.fetched_at` defaulting to `""` means any caller that still constructs a `RawDocument` without it (e.g. a hand-built test fixture) will have `detect_stale_data` correctly report it as stale, by design — not a silent success.
- Once ADR-0021 (LLM provider) is resolved, deeper `extract` behavior can be added behind the same method signature — no other method here has a shape dependency on how `extract` internally works.
