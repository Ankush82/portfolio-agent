# 0038 — Decision & Policy real mechanism: verified-claim scoring contract, weighted relevance/significance/risk rules, actionability thresholds, rate-limit policy, and a real pending-approval mechanism

**Status:** Accepted — 2026-08-26
**Component:** Decision & Policy (12)

## Context

`src/components/c12_decision_policy.py` was whiteboard-only before this pass — `DecisionPolicy(Protocol)` and `StubDecisionPolicy` only, no low-level design, no ADR. Its Protocol already fixes every method's signature (`assess_relevance(verified_claim: dict, portfolio: dict) -> float`, `assess_significance(verified_claim: dict) -> float`, `assess_risk(verified_claim: dict) -> float`, `determine_actionability(decision: Decision) -> str`, `authorize_action(action: dict) -> bool`, `enforce_policy(action: dict) -> bool`, `escalate(reason: str, context: dict) -> None`, `request_approval(action: dict) -> bool`) and the `Decision(verified_claim: dict, actionability: str)` dataclass — neither changed by this pass.

Read Analysis & Reasoning (08) first, as instructed, to confirm what this component actually receives. `DefaultAnalysisReasoning.test_hypotheses` (ADR-0037) returns `Hypothesis(claim, basis)` where `basis` carries `entity_id` (when the caller supplied one), `verified`, `confidence`, `evidence_count`, `was_contradictory` after a real hand-off to Evidence & Verification (09); `estimate_impact` separately returns `{"exposure": {...}, "significance": ..., "rationale": ...}`, `significance` being `DefaultClaimVerifier`/`reason_fn`-shaped judgment (`"unknown"` from the placeholder today, but the field is real and already the four-level shape assumed below wherever a real `reason_fn` fills it in). No prior ADR ever pinned down the exact merged dict shape that reaches `DecisionPolicy`'s methods once `Hypothesis.basis` and `estimate_impact`'s output are combined into one `verified_claim: dict` — that combination itself is a genuine design gap this pass has to resolve to be callable at all. Read Security & Privacy (17)'s `DefaultBoundaryGate.authorize` (ADR-0020) and Observability & Governance (16)'s `DefaultAuditManager` (ADR-0017) next, both already real; this component is required to call through the former for real rather than reimplement authorization, and to use the latter the same way `DefaultRecoveryManager.escalate` (component 10, ADR-0004/0015) already does.

Per this round's operating-mode instruction, every gap below is resolved here with documented engineering judgment (Status: Accepted, not Proposed) rather than left open, except one narrow, genuine piece: nothing anywhere in this project can yet mark a pending approval as approved (no UI, no notification-and-wait mechanism exists). That is not an LLM/external-credential gap in ADR-0021's sense — it doesn't need a reasoning backend or a live external API — so it does not get a `Proposed` placeholder ADR of its own; `request_approval` below is designed and shipped as a real, working pending-state mechanism, honestly incomplete only in that nothing external can flip its stored status yet.

## Decision

**The `verified_claim: dict` contract — the shape every method below reads, defined here since no prior ADR fixed it:**

```
{
  "claim": str,                 # Hypothesis.claim
  "entity_id": str | None,      # Hypothesis.basis["entity_id"]
  "confidence": float,          # Hypothesis.basis["confidence"] (0.0-1.0), from ClaimVerifier.verify (ADR-0031)
  "evidence_count": int,        # Hypothesis.basis["evidence_count"]
  "was_contradictory": bool,    # Hypothesis.basis["was_contradictory"]
  "significance": str,          # estimate_impact's judgment half: "high" | "medium" | "low" | "unknown"
  "exposure": dict,             # estimate_impact's real half: {"market_value": float, "weight": float}
  "relevance": float,           # 0.0-1.0, attached by the caller after running assess_relevance separately (see below)
}
```

Every key is read defensively (`.get(key, <conservative default>)`) — a missing key never crashes a scoring method, it scores as if the signal weren't there (`0.0`/`False`/`"unknown"`), the same "honest miss, not a forced guess" posture ADR-0035's `resolve_entity` already established. `relevance` is the one key this component itself is expected to attach, not Analysis & Reasoning — explained next.

**`assess_relevance(verified_claim, portfolio)`: real, delegated entirely to `DefaultUserPortfolio` (01), never reimplemented.** `portfolio: dict` (the Protocol's own fixed type — no `PortfolioSnapshot`/`User` dataclass exists at that parameter position) is treated as a bundle carrying whichever of `"portfolio_snapshot"` (a `PortfolioSnapshot`) or `"user"` (a `User`) the caller has on hand, mirroring the same `context.get("portfolio_snapshot")` convention `DefaultAnalysisReasoning._gather_analysis_input` (08, ADR-0037) already uses for the same kind of bundle. Rule, in priority order:

1. No `entity_id` on the claim → `0.0`. Nothing to check exposure against.
2. A `portfolio_snapshot` is present → call `UserPortfolio.calculate_exposure(snapshot)` for real and return that entity's `weight` (already a real 0.0-1.0 share of total portfolio market value, computed by `DefaultUserPortfolio.calculate_exposure` itself) — `0.0` when the entity isn't held at all. This is the continuous, real signal: "how much of this portfolio is this entity."
3. No snapshot but a `user` is present → call `UserPortfolio.determine_user_relevance(user, {"security_id": entity_id})` for real and map its boolean to `1.0`/`0.0` — the coarser fallback signal when only identity, not a live snapshot, is available.
4. Neither → `0.0`.

Because this method's `portfolio` parameter (not part of `verified_claim`) is the only place holding-exposure data is available, and `determine_actionability` below only receives a `Decision` built from `verified_claim` alone, the caller is expected to run `assess_relevance` first and attach its result onto the claim dict as `"relevance"` before constructing the `Decision` — the one field in the contract above this component doesn't compute from `verified_claim`'s own contents.

**`assess_significance(verified_claim)`: real, weighted combination of two signals already on the claim.** `SIGNIFICANCE_LEVEL_SCORES = {"high": 1.0, "medium": 0.6, "low": 0.3, "unknown": 0.0}` maps `estimate_impact`'s judgment-half string onto a number; the final score is `0.6 * confidence + 0.4 * level_score`, clamped to `[0.0, 1.0]`. Confidence carries the larger weight (0.6) because it's `DefaultClaimVerifier`'s own real, evidence-backed number (ADR-0031's independent-source-citation formula) — a harder, better-grounded signal than the `reason_fn`-judged (today: placeholder-judged, honestly `"unknown"`) significance level, which still contributes real signal once a real `reason_fn` exists, just not the majority vote.

**`assess_risk(verified_claim)`: real, combines this method's own `assess_significance` with how uncertain/contradictory the evidence was.** `risk = min(1.0, assess_significance(verified_claim) * (1.0 - confidence) + contradiction_penalty)`, where `contradiction_penalty = 0.3` when `was_contradictory` is `True`, else `0.0`. The `significance * uncertainty` term is deliberate: a claim that's both highly significant and highly confident is *low* risk to act on (acting on a well-evidenced, high-stakes claim is exactly what this system is for); risk climbs specifically when stakes and doubt combine — a significant claim we can't trust is the dangerous case, an insignificant uncertain claim is not. The flat `0.3` contradiction penalty is separate and additive because ADR-0014's automatic contradiction resolution, however good, is still explicitly flagged in that ADR's own Consequences as "exactly the shape of claim a human reviewer would want visibility into" — risk should reflect that regardless of how confident the resolved verdict ended up being.

**`determine_actionability(decision)`: real, threshold-based, reads `relevance`/`significance`/`risk` off `decision.verified_claim` (significance and risk recomputed via this class's own `assess_significance`/`assess_risk`; relevance read from the `"relevance"` key the caller already attached, per the contract above — `determine_actionability`'s fixed signature has no `portfolio` parameter to compute it fresh).**

```
RELEVANCE_SUPPRESS_THRESHOLD    = 0.05
ESCALATE_RISK_THRESHOLD         = 0.60
ESCALATE_SIGNIFICANCE_THRESHOLD = 0.70
NOTIFY_SIGNIFICANCE_THRESHOLD   = 0.30

if relevance < RELEVANCE_SUPPRESS_THRESHOLD:            "suppress"
elif risk >= ESCALATE_RISK_THRESHOLD
      or significance >= ESCALATE_SIGNIFICANCE_THRESHOLD: "escalate"
elif significance >= NOTIFY_SIGNIFICANCE_THRESHOLD:      "notify"
else:                                                     "suppress"
```

Relevance gates first and absolutely — an irrelevant claim (doesn't touch the user's actual holdings) is suppressed regardless of how significant or risky it looks in isolation, matching the whiteboard's own `-> Interaction & Notification (13)` interface intent: nothing not-relevant should ever reach notification. Above the relevance floor, high risk *or* high significance alone is enough to escalate (either "this is genuinely dangerous to get wrong" or "this genuinely matters a lot" independently justify a human-reviewed path, matching the Component Whiteboards' own three-way `"notify"`/`"escalate"`/`"suppress"` example); moderate significance notifies; everything else — relevant but too weak a signal to act on — suppresses. `decision.actionability` is set to the computed result before returning it (the dataclass is mutable, no new field added, matching its fixed `Decision(verified_claim, actionability)` shape), so a caller holding the same `Decision` object sees the real answer reflected on it, not just in the return value.

**`authorize_action(action)`: real, calls `BoundaryGate.authorize` for real, never bypassed or reimplemented.** `action: dict` supplies `"identity"`, `"action"`, `"resource"` (each defaulting to `""` when absent, `authorize`'s own fail-open posture per ADR-0020 already tolerates an empty string identity); this method's entire job is destructuring `action` into `authorize`'s three positional arguments and returning whatever it decides. Per ADR-0020, that decision is `True` today, every time, logged not enforced — this component inherits that interim posture rather than working around it, exactly as instructed.

**`enforce_policy(action)`: real, one concrete rule — a sliding-window notification rate limit per identity, backed by `Infrastructure`.** A new `"decision_policy_notifications"` table records one row per allowed action (`{"id", "identity", "issued_at", "action"}`, `issued_at` a real `time.time()` epoch float, matching the epoch-timestamp precedent `DefaultQuarantineGate` (06, ADR-0007) already uses for its own TTL window). On each call: query every row for `action.get("identity", "")` (`Infrastructure.query`'s filter dict is exact-match only — no native range query, so the window bound is applied client-side over the identity-filtered rows, the same pattern this project already uses wherever a numeric range is needed against this interface), count how many have `issued_at` within `_rate_limit_window_seconds` (default `3600.0`, one hour) of now; if that count is already `>= _rate_limit_max_per_window` (default `5`), the call is blocked (`False`, and an `AuditManager.record("policy_rate_limit_blocked", ...)` entry — a policy block is exactly the kind of governance event worth a durable trail), otherwise a new row is stored and the call is allowed (`True`). One rule, not elaborate policy machinery, per the task's own instruction — a real, useful frequency cap on how often this system can notify one person, not a general-purpose policy engine.

**`escalate(reason, context)`: real, records via `AuditManager`, matching `DefaultRecoveryManager.escalate`'s own pattern exactly.** `self._audit_manager.record("decision_policy_escalation", {"reason": reason, "context": context})` — same shape (`event_type`, structured detail dict), same reasoning: an escalation is exactly the class of event `AuditManager.record`'s docstring already names as audit-relevant, and component 10's `DefaultRecoveryManager.escalate` already established this component receives that same kind of hand-off (Reliability & Resilience's "escalate when no alternative tool" path, fig 15.1, also lands here per the module's own docstring).

**`request_approval(action)`: real — a genuine pending-approval mechanism backed by `Infrastructure`, honestly returning `False` until something external marks it approved.** A new `"decision_policy_pending_approvals"` table, one row per requested approval: `{"id", "action", "status", "requested_at"}`. `action.get("id")` is used as the row id when the caller supplies one (a stable identifier for "this specific action, asked about repeatedly" — the natural idempotency key); when absent, a fresh `uuid4` is generated, meaning each call with no `id` is treated as a distinct new request (never spuriously reports approved, since nothing tagged it that way). On each call: if a row for that id already exists, return whether its `status == "approved"` (still `False` today, since nothing external exists yet to change it — but the check itself is real, not hardcoded); otherwise store a new `"pending"` row, record an `AuditManager` event (`"approval_requested"`), and return `False`. This is the honest version of "genuinely real, even though nothing can approve it yet" the task asked for: the pending-state persistence, idempotency-by-id, and status check are all real working mechanism; only the human-in-the-loop UI/notification path that would ever flip `status` to `"approved"` doesn't exist anywhere in this project yet, which is a real, named gap, not a disguised placeholder.

## Alternatives considered

- **Making `assess_relevance` also read a `"relevance"`-precomputing shortcut off `verified_claim` itself, skipping `portfolio` entirely.** Rejected — the whole point of the task's instruction was to call `DefaultUserPortfolio.calculate_exposure`/`determine_user_relevance` for real rather than reinvent relevance scoring from whatever happens to already be on the claim; a shortcut would silently make the "call c01 for real" requirement optional depending on caller behavior.
- **Giving `Decision` a third field (e.g. `relevance: float`) so `determine_actionability` never has to reach into `verified_claim` for it.** Rejected — the task fixed `Decision(verified_claim: dict, actionability: str)` exactly; adding a field would be an unauthorized change to an already-specified dataclass, not a real gap this pass is free to resolve by fiat.
- **A single combined 0-1 "priority" score instead of three separate relevance/significance/risk numbers feeding threshold logic.** Rejected — the Protocol already exposes `assess_relevance`/`assess_significance`/`assess_risk` as three separately callable, separately testable methods; collapsing them into one opaque score before `determine_actionability` sees them would make each individual method's real behavior harder to verify and would throw away exactly the kind of "why did this escalate" transparency a governance component should have.
- **Enforcing `authorize_action`'s decision (raising or blocking on `False`) inside this component.** Rejected — ADR-0020 is explicit that `DefaultBoundaryGate.authorize` is fail-open and not yet a real enforcement boundary; this component's job per the task brief is to call through it for real, not to compensate for its known interim behavior by inventing its own enforcement on top, which would silently resolve ADR-0020's still-open granularity question by whatever this component happened to do.
- **A token-bucket or leaky-bucket rate limiter for `enforce_policy` instead of a simple sliding window count.** Rejected as more machinery than the task asked for ("don't invent elaborate policy machinery, one real, useful, documented policy check is enough") — a sliding window over stored timestamps is simpler, fully real, and answers the same question ("has this identity been notified too often recently") just as correctly for this pass's purposes.
- **Treating `request_approval` as out of scope / a `Proposed` placeholder ADR, the same treatment as ADR-0021/ADR-0023/ADR-0027.** Rejected per the task's own explicit instruction: this is not a reasoning/external-credential gap (no LLM, no third-party API is needed to persist a pending-approval record and check its status), so it doesn't fit ADR-0021's template — it's a real mechanism this pass can and does build, honestly incomplete only in that nothing external can approve a request yet.

## Consequences

- `assess_relevance`'s continuous exposure-weight signal (when a `portfolio_snapshot` is available) and its coarser boolean fallback (`user` only) are genuinely different-shaped signals — a caller that only ever supplies `user` will see relevance values of exactly `0.0` or `1.0`, never anything in between, which changes how close to `RELEVANCE_SUPPRESS_THRESHOLD` (`0.05`) a decision can land. Both paths are real, neither is a placeholder; this is a documented consequence of the two different `UserPortfolio` methods this component is instructed to call, not an inconsistency to fix here.
- `determine_actionability` recomputing `significance`/`risk` from `verified_claim` (rather than trusting precomputed values a caller might pass) means calling `assess_significance`/`assess_risk` separately before building a `Decision` is redundant but harmless — both are pure functions of `verified_claim`'s contents, so recomputation always agrees with a prior call given the same dict.
- `enforce_policy`'s rate-limit table grows without bound (no eviction of old rows) — acceptable for this pass the same way `DefaultQuarantine* `/`DefaultAuditManager`'s own append-only logs are; a real retention/cleanup policy is a separate concern this ADR doesn't attempt to solve.
- `request_approval`'s pending rows can never be seen or acted on by a human today — there is no UI, no notification channel, no `mark_approved` entry point anywhere in this project. Anything that depends on an approval actually completing is not yet safe to build on top of this method; it is safe to build on top of its pending-state bookkeeping and idempotency being real.
- The `verified_claim` dict contract defined here is now the de facto interface between Analysis & Reasoning (08) and Decision & Policy (12) — if a future pass changes `Hypothesis.basis`'s keys or `estimate_impact`'s output shape, this component's scoring rules (which key names they read) need to be revisited alongside that change, the same coupling ADR-0037 already flagged between `Hypothesis` and `Claim`.
