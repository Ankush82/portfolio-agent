# 0010 — Memory technology: Mem0

**Status:** Accepted — 2026-08-26 (vendor picked); vendor fit against the four decisions below formally verified 2026-08-26 during component 06's real implementation pass — see Consequences for the per-decision result.
**Component:** Memory (06)

## Context

With Memory's design complete and confirmed — active working-set management (ADR-0005), linked network structure (ADR-0006), quarantine-at-write (ADR-0007), structural partition (ADR-0008) — a concrete storage/technology approach needed to be chosen for it, against that design rather than in the abstract.

## Decision

A purpose-built memory layer — **Mem0** — over building the storage ourselves and over Supermemory. Open-source and self-hostable, chosen directly by the user; not selected via the formal per-decision evaluation this ADR originally called for (see Consequences — that check is now the responsibility of whoever implements component 06 for real).

## Alternatives considered

- **Unified store (PostgreSQL + pgvector + adjacency tables).** One system implements all four decisions directly: separate schemas for the partition, a status column for quarantine, adjacency tables for links, pgvector for retrieval. Rejected as the default because it means building and maintaining all four mechanisms by hand, when tools already exist that claim to solve pieces of this.
- **Specialized per concern (knowledge graph for links + vector DB for retrieval + Postgres for scope/quarantine bookkeeping).** Each piece is the best tool for that one job. Rejected because keeping three systems consistent with each other is its own ongoing cost, for a component whose write path already has four sequential gates to keep consistent internally.

## Consequences

**The evaluation this ADR originally required has now happened**, against `mem0ai` 2.0.19 (the current PyPI release as of this pass — confirmed installable via `uv pip install mem0ai`, and its source inspected directly under `.venv/lib/python3.11/site-packages/mem0/`, not assumed from memory or from older documentation). Result, per decision — Mem0 turns out to genuinely fit none of the four cleanly on its own:

- **Structural partition (ADR-0008): does not fit.** Mem0's own scoping (`Memory.add`/`search`/`get_all`, `mem0/memory/main.py`) is `user_id`/`agent_id`/`run_id` passed as metadata filters into one shared vector-store collection — `search()` literally requires `filters={"user_id": ...}` and rejects top-level scope arguments, but there is no concept of two physically distinct stores. This is exactly the "single store, scope as metadata" alternative ADR-0008 rejected by name. **Decision: `DefaultScopeRouter` implements the physically-separate-store version directly against `DefaultInfrastructure`** — two distinct table namespaces, `memory_user` and `memory_shared` — rather than trusting Mem0's filter to enforce a boundary ADR-0008 specifically didn't want enforced by a filter.
- **Quarantine-at-write (ADR-0007): does not fit.** Mem0 has `expiration_date` (a TTL for hiding a memory from `search`/`get_all`) and a per-memory `history()` audit trail (ADD/UPDATE/DELETE events), but nothing resembling a pre-store trust gate — no "pending/unverified, not yet readable" state a memory sits in before it's usable. Everything passed to `add()` is immediately live. **Decision: `DefaultQuarantineGate` is `DefaultInfrastructure`-backed directly** — a dedicated `memory_quarantine` table with real pending/released/expired bookkeeping (ADR-0007's own lifecycle), plus provenance tagging via `BoundaryGate.tag_provenance` and an audit record via `AuditManager` (both cross-cutting hooks the write path is supposed to go through regardless of storage vendor).
- **A-MEM-style explicit linking (ADR-0006): does not fit.** As of the 2026 OSS release, `mem0ai` ships **no graph store integration at all** — Neo4j, Memgraph, Kuzu, Apache AGE, and Neptune support were all removed from the self-hosted package; graph memory is now Mem0 Platform (hosted) only (confirmed via `mem0.vector_stores`/`mem0.configs.vector_stores` containing no graph backend, and via web search on the 2026 OSS/Platform split). What OSS Mem0 does instead is similarity search at *read* time via `search()` — relatedness discovered on demand, never persisted as structure — which is precisely the "independent records" alternative ADR-0006 rejected. **Decision: `DefaultEntityLinker` computes links directly** — deterministic Jaccard token-overlap between a candidate's content and each existing memory's content, above a threshold, at write time, with the resulting ids persisted into `Memory.links` (the JSONB field already on the record) via `DefaultInfrastructure`. This is real structural relatedness, not semantic relatedness — flagged in the code as a known limitation, not represented as equivalent to A-MEM's LLM-driven analysis.
- **Active working-set management (ADR-0005): does not fit.** Mem0 is architecturally a passive store — `add`/`search`/`get_all`/`update`/`delete`, all callee-initiated, nothing that curates a bounded active set or evicts on its own. **Decision: `DefaultMemoryManager` implements a real bounded in-memory working set (default size 50) with LRU eviction** — `OrderedDict`-backed, evicting the least-recently-touched entry when full — persisting through `DefaultScopeRouter`/`DefaultInfrastructure` on admit. LRU covers the "recency" half of fig. 2's "recency and relevance, not just age" eviction policy; a relevance-weighted score is not implemented in this pass (would need a real similarity/importance model) — named here, not silently dropped, as this ADR's remaining known-unknown.

**The one thing Mem0 would add real value for — LLM-driven fact extraction and dedup (`add(..., infer=True)`, which decides ADD/UPDATE/DELETE against existing memories) — needs an LLM API key** (OpenAI by default; configurable to other providers including Anthropic, but every option needs *some* provider credential), and embeddings for its own `search()` need an embedding provider with the same constraint (a local/offline embedder exists but needs an extra dependency and a model download, not a zero-config path). No LLM provider has been chosen anywhere in this project for any component (the same gap ADR-0021 already named for Agent Runtime) — so this is a genuine external-credential gap, not a design gap. **Decision: Mem0 is not wired into the real write/read path this pass.** The credential-gated integration point is documented separately, Proposed, in [ADR-0028](0028-memory-mem0-llm-embedding-provider-interim.md), mirroring ADR-0021's shape exactly — `DefaultInfrastructure`-backed logic (above) is the default path so the rest of Memory works without it, and Mem0 stays available to wire in for real once a provider decision exists.
- The fallback alternatives this ADR originally listed (unified Postgres+pgvector store, or specialized-per-concern) are, in effect, what got built for three of the four decisions — not because Mem0 was rejected as a vendor, but because its actual OSS feature set in 2026 turned out not to cover structural partition, quarantine, or explicit linking, and its one differentiating capability is blocked on the same credential gap as Agent Runtime's reasoning.
- `mem0ai` was installed and inspected (`uv pip install mem0ai`, not `uv add`) for this research; it is **not** added to `pyproject.toml` as a project dependency, since nothing in this pass ends up calling it for real. Re-installing it later is a one-line `uv add mem0ai` once ADR-0028 is resolved.
