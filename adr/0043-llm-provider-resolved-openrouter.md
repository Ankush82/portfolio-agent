# 0043 — LLM provider resolved: OpenRouter, one shared `reason_fn`

**Status:** Accepted — 2026-08-26
**Component:** Agent Runtime (10), Analysis & Reasoning (08)

## Context

ADR-0021 named the gap for Agent Runtime's `reason`/`assess_stakes` nodes: no ADR or design artifact anywhere in this project had ever chosen an LLM provider, so `build_agent_runtime_graph()` shipped `placeholder_reason_fn` behind an injectable `reason_fn: Callable[[dict], dict]` seam instead. ADR-0037 hit the exact same root cause independently while building Analysis & Reasoning's `infer`/`generate_hypotheses`/`generate_explanations`/`generate_counterarguments`/`synthesize_findings`/`estimate_impact` — restated there rather than duplicated, per that ADR's own text — and shipped its own `placeholder_reason_fn` behind the identical `Callable[[dict], dict]` contract.

Both gaps are the same decision: which LLM provider backs this project's actual reasoning. ADR-0021 named three real alternatives (Anthropic Claude API, OpenAI API, a locally-hosted open model) without picking one, deliberately leaving cost, latency, and data-handling tradeoffs for the user to weigh. That decision is made here, once, for both callers — not decided twice.

## Decision

**OpenRouter**, an OpenAI-compatible gateway, called directly over HTTP via `requests` — no vendor SDK. One new module, `src/llm.py`, is the only place in the codebase that reads `OPENROUTER_API_KEY` or talks to OpenRouter; `get_reason_fn(placeholder, audit_manager=None)` is the selection function both callers use, returning the real `openrouter_reason_fn` when a key is configured (environment variable or a `.env` file at the repo root) and the caller's own `placeholder` otherwise — the same `Default*`-vs-`Stub*` pattern this codebase already applies everywhere (`DefaultInfrastructure`/`StubInfrastructure`).

**Model: `anthropic/claude-haiku-4.5`**, chosen for the specific shape of the calls both callers actually make — bounded, structured judgment calls (decide a next action, assess stakes, hypothesize, judge significance), not open-ended generation — where a fast, cheap model is capable enough and per-call latency matters more than maximum capability. `OPENROUTER_MODEL` is one named constant, not per-phase configuration; nothing in either caller's request shape varies by phase in a way that would justify different models per phase.

**Both `build_agent_runtime_graph()` and `DefaultAnalysisReasoning.__init__` now default `reason_fn` to `None`, resolving it via `get_reason_fn` at call/construction time**, rather than requiring every caller to pass a `reason_fn` explicitly. Passing one explicitly — as every existing test in `tests/components/test_agent_runtime.py` and `tests/components/test_analysis_reasoning.py` already does with each module's own `placeholder_reason_fn` — always wins over environment-based resolution, so no existing test's behavior changed. This is why neither test file needed logic changes beyond how they construct the object under test.

**Prompts and response parsing are real, phase-specific, and one-directional.** `_build_messages(phase, request)` builds a real system prompt naming that phase's actual job (not one generic prompt reused across all eight phases: `reason`, `assess_stakes`, `infer`, `generate_hypotheses`, `generate_explanations`, `generate_counterarguments`, `synthesize_findings`, `estimate_impact`) plus a JSON-serialized user prompt built from the phase's real request payload. `_normalize_response(phase, parsed, request)` converts the model's parsed JSON back into the exact shape each phase's own `placeholder_reason_fn` already returns, so a real response and a placeholder response are interchangeable to every existing caller — no caller-side code needed to change to accept real output.

**A degraded-but-attempted call fails toward safety, not silence.** `_fallback_response(phase)` is used only after a key was genuinely configured and a real HTTP call was genuinely made but failed (timeout, rate limit, non-2xx status) or came back unparseable. Two phases deliberately do not mirror the placeholder's own shape: `"reason"` reports `checkpoint_complete: True` (so a persistently broken API degrades the graph to a bounded stop, never an infinite reason-loop retrying a dead call) and `"assess_stakes"` reports `stakes_high: True` (so a degraded call is flagged for reflection, never silently treated as low-stakes). Every fallback use is recorded via `AuditManager` (`openrouter_call_degraded`), so a degraded call is visible in the audit trail rather than indistinguishable from a real answer.

**A missing key is a named, specific error, never a silent fallback.** `openrouter_reason_fn` raises `MissingOpenRouterAPIKeyError` if `OPENROUTER_API_KEY` genuinely isn't set when it is actually invoked. The fallback path above only exists for a call that was attempted and failed after the key was present — `get_reason_fn` is the one place that chooses between the real function and a placeholder, and it makes that choice once, before either is ever called, so no caller gets a blend of the two.

## Alternatives considered

- **Anthropic Claude API directly (the SDK, ADR-0021's first-named option).** Rejected in favor of OpenRouter as the transport: OpenRouter is itself an OpenAI-compatible gateway that can route to Claude models (as it does here, via `anthropic/claude-haiku-4.5`) alongside every other major provider, so choosing OpenRouter does not foreclose Claude — it adds a provider-switching seam (a single `OPENROUTER_MODEL` string) that calling the Anthropic SDK directly would not have, at the cost of one intermediary hop. Given this project's own reasoning calls are latency-sensitive but not latency-critical (a network round trip already exists in every LLM-backed design considered), that tradeoff favors the seam.
- **OpenAI API directly.** Same reasoning as above — subsumed by OpenRouter's ability to route to it without a second, provider-specific integration.
- **A locally-hosted open model.** Still rejected for the reason ADR-0021 already named: it trades per-call API cost and external network latency for an operational burden (hosting, serving, keeping a model current) this project has no infrastructure for today. Revisit only if OpenRouter's per-call cost or data-handling posture becomes a real problem at production volume.
- **The `openai` Python SDK, instead of raw `requests`.** Rejected: OpenRouter already speaks the OpenAI wire format over plain HTTP, and `requests` is already a resolved transitive dependency of this project's own `langgraph` → `langsmith` chain (confirmed via `uv.lock` before adding it directly to `pyproject.toml`) — an SDK dependency would add nothing beyond what a POST and a Bearer header already accomplish.
- **A separate `reason_fn` implementation per caller (one for Agent Runtime, one for Analysis & Reasoning)**, since ADR-0021 and ADR-0037 each named the gap independently. Rejected: both callers already share the exact same `Callable[[dict], dict]` contract by construction (neither ADR invented a new shape), and the only real difference between the two is which phases each caller ever requests — `_build_messages`/`_normalize_response`'s per-phase dispatch already handles that without needing two modules.
- **Choosing a model per phase** (e.g. a larger model for `synthesize_findings`, a smaller one for `assess_stakes`). Rejected as premature: nothing in this project has measured a quality gap that would justify it, and one shared, named constant (`OPENROUTER_MODEL`) is the smallest real mechanism that answers the actual question today — a per-phase model map can be added later without changing any caller's contract, the same way the model itself can be swapped by changing one constant.

## Consequences

- Agent Runtime's `reason`/`assess_stakes` nodes and Analysis & Reasoning's six cognitive methods now do real inference whenever `OPENROUTER_API_KEY` is configured — the first real, non-placeholder reasoning anywhere in this project. Without a key, both callers behave exactly as they did under ADR-0021/ADR-0037: `placeholder_reason_fn`, unchanged in either file.
- `pyproject.toml` gains `requests>=2.31` as a direct dependency (previously only transitive); `uv.lock` regenerated to match.
- `src/llm.py` is the only module in this codebase that imports `requests` for an LLM call or reads `OPENROUTER_API_KEY` — both `c10_agent_runtime.py` and `c08_analysis_reasoning.py` import `get_reason_fn` from it rather than each maintaining its own HTTP/parsing logic. A future component with its own cognitive gap (e.g. Evidence & Verification's contradiction resolution, Retrieval & Context's Self-RAG gate) can reuse this same module rather than inventing a fourth `reason_fn` backend.
- Real API cost and network latency are now live risks on Agent Runtime's and Analysis & Reasoning's hot paths whenever a key is configured — `_REQUEST_TIMEOUT_SECONDS = 30` bounds the worst case per call, and the fail-toward-safety fallback bounds what happens when a call is genuinely lost, but neither eliminates the cost/latency ADR-0021 already flagged as real considerations.
- `_normalize_response("synthesize_findings", ...)` imports `Hypothesis` from `components.c08_analysis_reasoning` at call time, not at module top — a deliberate, documented deferred import to avoid a circular import (`c08_analysis_reasoning` imports `get_reason_fn` from `src/llm.py`). This is the one place `src/llm.py` knows about a specific component dataclass; every other function in the module stays component-agnostic by converting dataclasses generically (`_json_safe`) rather than importing them.
- ADR-0021 is superseded by this ADR — its placeholder mechanism and injectable-seam design remain exactly as built (nothing about the graph's shape changed, exactly as ADR-0021's own Consequences predicted), but the "which provider" question it deliberately left open is now answered.
- This is scoped to Agent Runtime's and Analysis & Reasoning's `reason_fn` seams only. Other components' genuine external-dependency gaps (ADR-0023 broker API, ADR-0027 data-fetch provider, ADR-0028 Mem0's own LLM/embedding provider, ADR-0034 corrective-retrieval search provider, ADR-0040 notification delivery channel) are unaffected — none of them share this exact `reason_fn` contract, so none of them are resolved by this decision.
